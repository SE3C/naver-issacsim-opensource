# 자동평가 Tracking Score·Survival Rate 구조 분석 보고서

-   작성 기준: 팀 시리우스 열무의 1차 질의에 대한 운영진 공개 답변
-   분석 범위: 현재 공개 답변으로 직접 확인 가능한 평가 구조와 그로부터
    도출 가능한 해석
-   제외 범위: 아직 답변되지 않은 추가 질의, 시나리오별 비공개 명령값,
    공개되지 않은 최종 점수 변환식
-   작성일: 2026-09-24

## 1. 목적

본 문서는 자동평가의 `Tracking Score`와 `Survival Rate`를 학습 정책
개선에 활용하기 위해, 운영진이 공개한 답변을 평가 절차 관점에서 재구성한
분석 보고서다.

특히 다음을 구분한다.

-   **확인 사실**: 운영진 답변에서 직접 확인되는 내용
-   **해석**: 확인 사실로부터 평가 결과를 읽을 때 합리적으로 도출되는
    의미
-   **미확인 사항**: 현재 공개 답변만으로 확정할 수 없는 내부 계산

------------------------------------------------------------------------

## 2. 핵심 결론

현재 답변으로 확인된 평가 구조는 다음과 같다.

1.  Tracking 오차는 매 step에서 `x 선속도`, `y 선속도`, `yaw 각속도`
    오차를 하나의 벡터 크기로 묶어 계산한다.
2.  세 성분의 비중은 같다고 공개되었다.
3.  각 episode에서는 매 step 오차를 단순 평균한다. 순간 최대 오차에 별도
    가중치를 주지 않는다.
4.  낙상 episode도 낙상 전까지의 구간으로 Tracking 평균 오차를 계산한다.
5.  명령 변경 직후의 가속·감속 구간과 episode 시작 직후의 출발 구간도
    Tracking 평가에서 제외하지 않는다.
6.  선속도는 world frame이 아니라 로봇 몸통 기준 frame으로 평가한다.
7.  Tracking은 episode마다 평균 오차를 먼저 계산하며, 짧게 종료된
    episode도 다른 episode와 같은 비중으로 반영된다.
8.  Survival에서는 제한시간까지 진행한 episode를 생존, 몸통 바닥
    접촉으로 종료된 episode를 실패로 처리한다.
9.  평가 종료 시점에 아직 넘어지지 않고 진행 중인 로봇도 생존으로
    처리한다.
10. 모든 제출은 같은 seed로 평가하지만, 정책별 낙상 시점 차이로 이후
    명령 sequence가 달라질 수 있으므로 모든 조건이 완전히 동일하다고
    보장되지는 않는다.
11. 명령은 학습과 같은 방식으로 생성되며, episode 시작 시 정한 뒤
    10초마다 다시 뽑는다. 고정값 시나리오는 사실상 일정하고 범위형
    시나리오는 10초마다 범위 내 새 값이 나온다.

이 정보만으로도 evaluator의 상당 부분을 이해할 수 있지만, **평균 오차를
최종 Tracking Score로 변환하는 함수와 일부 집계 세부사항은 아직 공개되지
않았다.**

## 3. Tracking 오차 구조

### 3.1 매 step의 오차

운영진 설명에 따르면 매 step에서 다음 세 오차를 함께 사용한다.

-   x 방향 선속도 오차
-   y 방향 선속도 오차
-   yaw 각속도 오차

이를 하나의 오차 크기, 즉 세 성분을 합친 벡터의 길이로 만든다.

공개 답변을 수식 형태로 표현하면 다음 구조로 이해할 수 있다.

``` text
e_t = sqrt(
    error_vx(t)^2
  + error_vy(t)^2
  + error_yaw(t)^2
)
```

여기서 `e_t`는 특정 step의 Tracking 오차 크기다.

### 3.2 세 성분의 비중

운영진은 세 성분의 비중이 같다고 명시했다.

따라서 현재 공개 정보상 특정 축만 별도의 더 큰 가중치로 평가한다는
근거는 없다.

다만 다음 사항은 아직 확정되지 않았다.

> `m/s` 단위의 x·y 선속도 오차와 `rad/s` 단위의 yaw 각속도 오차를
> 내부적으로 normalization 또는 scale 보정한 뒤 동일 비중으로 합치는지,
> 아니면 수치 자체를 그대로 합치는지는 현재 답변만으로 확정할 수 없다.

따라서 예를 들어 `0.5 m/s`의 선속도 오차와 `0.5 rad/s`의 yaw 오차가 최종
벡터 계산에서 완전히 동일한 수치 기여도를 갖는다고 아직 단정해서는 안
된다.

## 4. Episode 내부 Tracking 집계

### 4.1 단순 평균

운영진은 각 step의 오차를 episode 동안 단순 평균한다고 밝혔다.

따라서 episode `i`의 평균 오차는 개념적으로 다음과 같다.

``` text
E_i = (e_1 + e_2 + ... + e_T) / T
```

### 4.2 큰 순간 오차에 대한 별도 페널티 없음

최댓값을 따로 평가하거나 큰 오차를 제곱하는 등, 큰 순간 오차를 별도로
증폭시키는 구조는 아니라고 답변되었다.

따라서 큰 오차의 영향은 기본적으로 다음 두 요소에 의해 결정된다.

-   얼마나 큰 오차였는가
-   얼마나 오래 지속되었는가

이 구조에서는 짧은 순간의 큰 spike보다 작더라도 지속적으로 발생하는
tracking bias가 전체 평균에 상당한 영향을 줄 수 있다.

즉 영상이나 로그를 해석할 때 순간적인 overshoot만 볼 것이 아니라 다음과
같은 지속 오차도 중요하게 확인해야 한다.

-   목표 속도보다 계속 느리거나 빠른 상태
-   횡방향 속도가 지속적으로 남는 상태
-   yaw 명령에 대한 지속적인 부족/과잉 회전
-   명령 변경 후 새로운 목표에 수렴하는 데 오래 걸리는 상태

## 5. 낙상과 Tracking의 관계

### 5.1 낙상 전 구간도 Tracking에 포함

로봇이 중간에 넘어져 episode가 종료되어도 해당 episode를 Tracking에서
제거하지 않는다.

넘어지기 전까지의 step들로 평균 오차를 계산하고 그 결과를 Tracking에
반영한다.

### 5.2 낙상은 Tracking과 Survival 양쪽에 영향을 줄 수 있음

운영진은 넘어지는 순간 속도가 크게 어긋나므로 해당 episode의 평균
Tracking 오차가 나빠지기 쉽다고 설명했다.

동시에 Survival에서는 해당 episode를 실패로 처리한다.

따라서 낙상은 단순히 Survival만 감소시키는 사건으로 해석하기 어렵다.

정책이 자주 넘어지는 경우:

``` text
낙상
 ├─ Survival 실패 증가
 └─ 짧고 Tracking이 좋지 않은 episode 생성 가능
```

이라는 두 경로가 동시에 발생할 수 있다.

이는 안정성 개선이 Survival에만 영향을 주는 것이 아니라 Tracking
결과에도 간접적으로 긍정적인 영향을 줄 가능성이 있음을 의미한다.

단, **안정성 reward를 강화하면 반드시 Tracking Score가 상승한다는
인과관계까지 이 답변으로 증명되는 것은 아니다.** 실제 정책의 속도 추종
성능 변화까지 함께 확인해야 한다.

## 6. Episode 길이와 Tracking 가중치

운영진 답변에서 특히 중요한 부분은 episode마다 평균 오차를 먼저
계산하고, 모든 episode를 같은 비중으로 평균한다는 설명이다.

즉 긴 episode가 단순히 step 수가 많다는 이유로 짧은 episode보다 더 큰
가중치를 갖는 방식은 아니다.

예를 들어 개념적으로:

``` text
Episode A: 20초 생존 → 평균 오차 E_A
Episode B:  3초 후 낙상 → 평균 오차 E_B

전체 집계에서는 E_A와 E_B가 각각 episode 하나로 반영
```

된다.

따라서 빨리 넘어지는 episode도 Tracking 집계에서 무시되지 않는다.

### 6.1 중요한 결과

자주 넘어지는 정책에서는 동일한 평가 시간 동안 짧은 episode가 반복적으로
생성될 수 있다.

운영진은 이러한 짧은 episode도 하나의 episode로 센다고 명시했으며, 이
때문에 자주 넘어지는 정책은 Tracking과 Survival 모두에 크게 반영될 수
있다고 설명했다.

다만 최종 Tracking 집계가 정확히 다음 중 어느 구조인지는 아직 완전히
공개되지 않았다.

#### 가능 구조 A

``` text
step error
→ episode 평균 error
→ episode별 Tracking score 변환
→ episode Tracking score 평균
```

#### 가능 구조 B

``` text
step error
→ episode 평균 error
→ episode 평균 error들을 전체 평균
→ 최종 Tracking score 변환
```

error-to-score 변환이 비선형이라면 A와 B는 서로 다른 결과를 만들 수
있다.

현재 답변은 `episode마다 평균 오차를 먼저 계산한다`는 것까지는
확정하지만, **최종 Tracking Score 변환이 정확히 어느 단계에 적용되는지는
추가 확인이 필요하다.**

## 7. 명령 변화와 transient response

### 7.1 명령 변경 직후도 그대로 평가

운영진은 다음 구간을 별도로 제외하지 않는다고 밝혔다.

-   episode 시작 후 정지 상태에서 출발하는 구간
-   목표 명령이 바뀐 직후의 가속 구간
-   목표 명령이 감소한 직후의 감속 구간

즉 steady-state tracking만 평가하는 구조가 아니다.

### 7.2 평가 관점

정책의 Tracking 성능을 판단할 때 다음 전체 과정이 중요하다.

``` text
정지
→ 출발
→ 목표 속도 접근
→ 정상 추종
→ command 변경
→ 가속/감속 또는 회전
→ 새로운 목표에 재수렴
```

따라서 고정 명령에서 오랫동안 안정적으로 목표 속도를 유지하는 능력만으로
Tracking 성능을 충분히 설명할 수 없다.

명령 변화에 대한 응답 속도와 안정성도 실제 평가에 직접 포함된다.

------------------------------------------------------------------------

## 8. 명령 생성 방식

운영진 답변에 따르면 명령은 학습 때와 같은 방식으로 생성된다.

### 8.1 기본 구조

-   episode 시작 시 명령 생성
-   이후 10초마다 명령 재생성

### 8.2 시나리오 종류에 따른 차이

고정값 시나리오는 명령을 다시 생성해도 같은 값이므로 사실상 episode 동안
일정하다.

범위형 시나리오는 10초마다 해당 범위 안에서 새로운 값이 생성된다.

따라서 범위형 시나리오에서는 정책이 하나의 목표 속도만 잘 따라가는 것이
아니라 여러 목표 명령 사이의 전환에도 대응해야 한다.

### 8.3 미공개 사항

시나리오별 구체적인 명령 값 또는 명령 범위는 공개되지 않았다.

따라서 현재 정보만으로 evaluator의 정확한 command distribution을
복제했다고 주장해서는 안 된다.

------------------------------------------------------------------------

## 9. 좌표계

Tracking에 사용되는 실제 선속도는 world frame이 아니라 **로봇 기준
frame**이다.

운영진 설명:

-   로봇이 바라보는 방향 = x
-   로봇의 옆 방향 = y
-   명령도 같은 기준

따라서 로봇이 world 좌표계에서 어느 방향을 바라보고 있느냐 자체보다,
현재 몸통 방향을 기준으로 명령된 전후·좌우 속도를 얼마나 정확히
수행하는지가 중요하다.

특히 선속도와 yaw 명령이 동시에 존재하는 복합 동작을 해석할 때 이 점을
고려해야 한다.

## 10. Survival 판정

### 10.1 생존과 실패

운영진 답변에 따르면:

-   제한시간까지 진행 → 생존
-   학습과 같은 종료 조건인 몸통의 바닥 접촉으로 종료 → 실패
-   전체 평가 시간이 끝날 때 아직 넘어지지 않고 진행 중 → 생존

으로 처리한다.

따라서 timeout과 fall termination은 평가에서 명확히 다른 결과다.

### 10.2 reset 후 계속 평가

넘어진 로봇은 평가에서 제거되지 않고 다시 시작하여 새 episode로 평가를
계속한다.

따라서 평가 시간 동안 하나의 병렬 로봇이 여러 episode를 만들 수 있다.

### 10.3 아직 남아 있는 집계 질문

현재 답변으로 낙상 후 새 episode가 생성된다는 사실은 확인되었다.

다만 Survival 최종 집계에서 예를 들어 한 로봇이 여러 번 종료되어 여러
개의 짧은 episode를 생성했을 때, **각 episode가 정확히 독립적인 동일
가중치 Survival sample로 분모에 들어가는지**는 후속 질문에서 명시적으로
확인할 가치가 있다.

현재 답변은 그 방향을 강하게 시사하지만, 정확한 최종 집계식을 공개했다고
보기는 어렵다.

------------------------------------------------------------------------

## 11. 동일 seed와 평가 재현성

모든 제출은 같은 seed로 평가한다.

따라서 시작 조건은 제출 간 동일하게 맞추려는 구조이며, 동시에 수백 대의
로봇 결과를 평균하기 때문에 운영진은 평가 결과 차이가 적다고 설명했다.

그러나 완전한 episode-by-episode 동일 조건 비교는 보장되지 않는다.

이유는 정책마다 낙상 시점이 달라질 수 있기 때문이다.

예를 들어:

``` text
Policy A → 5초에 낙상 → reset → 새로운 command 생성
Policy B → 계속 생존 → 기존 episode와 command 진행
```

처럼 정책 행동 자체가 이후 평가 진행 경로를 갈라놓을 수 있다.

따라서 같은 seed는 높은 재현성을 제공하지만, 두 정책이 평가 전체에서
완전히 동일한 command·episode sequence를 경험한다는 의미는 아니다.

## 12. 정책 개선 관점에서의 의미

### 12.1 안정성과 Tracking을 완전히 독립적으로 보면 안 됨

낙상은 Survival 실패를 만들 뿐 아니라 낙상 episode의 Tracking 평균에도
영향을 줄 수 있다.

따라서 다음과 같은 단순 구분은 실제 evaluator를 완전히 설명하지 못한다.

``` text
안정성 reward → Survival만 개선
Tracking reward → Tracking만 개선
```

실제로는 안정성이 Tracking 집계에도 영향을 줄 수 있고, 반대로 과도한
안정성 최적화가 속도 응답을 둔화시킨다면 Tracking을 악화시킬 수도 있다.

그러므로 실험에서는 두 지표를 함께 확인해야 한다.

### 12.2 평균 추종 성능이 중요

순간 최대 오차에 별도 penalty가 없으므로 정책 개선에서는 단발성 spike뿐
아니라 지속적인 오차를 줄이는 것이 중요하다.

특히 다음을 분리해서 확인할 가치가 있다.

-   x tracking error
-   y tracking error
-   yaw tracking error
-   command 변경 후 수렴 시간
-   fall 직전 tracking 붕괴
-   정상 보행 중 지속 bias

### 12.3 command transition을 별도 검증할 필요

평가가 transition 구간을 제외하지 않으므로 자체 evaluator나 영상
검증에서도 고정 명령만 보는 것은 부족하다.

정지 출발, 감속, 방향 전환, yaw 변경 등 command transition을 포함한
테스트가 실제 자동평가 해석에 더 적합하다.

------------------------------------------------------------------------

## 13. H1 분석에 대한 직접적인 시사점

현재 H1 실험에서는 속도 추종과 안정성을 별도 축으로 분석해 왔다.

이번 공개 답변은 그 구분 자체를 부정하지 않지만, 최종 evaluator에서는 두
축이 상호작용한다는 점을 더 명확히 보여준다.

예를 들어 H1 정책에서:

-   생존 시간이 증가했는가
-   base contact termination이 감소했는가
-   x/y tracking이 유지 또는 개선되었는가
-   yaw tracking이 유지 또는 개선되었는가
-   command 변경 직후 회복 시간이 짧아졌는가

를 함께 보는 것이 적절하다.

특히 단순히 평균 episode length가 증가했다는 이유만으로 최종 자동평가가
좋아졌다고 단정해서는 안 된다. 오래 살아남으면서 지속적인 속도 오차가
커질 수도 있기 때문이다.

반대로 Tracking error가 조금 낮아졌더라도 낙상이 크게 증가한다면 짧은
실패 episode의 반복과 Survival 감소 때문에 최종 결과가 나빠질 수 있다.

------------------------------------------------------------------------

## 14. 현재까지 확정할 수 없는 사항

현재 운영진 답변만으로 다음 사항은 확정할 수 없다.

1.  x·y 선속도와 yaw 각속도를 합치기 전에 단위 또는 범위 normalization을
    수행하는지
2.  episode 평균 error를 최종 Tracking Score로 변환하는 정확한 함수
3.  episode별로 먼저 score를 만든 뒤 평균하는지, 평균 error를 전체
    집계한 뒤 한 번 score로 변환하는지
4.  Tracking Score의 clip, threshold, exponential 또는 기타 비선형 변환
    여부
5.  Survival 최종 집계에서 여러 번 reset된 각 episode가 정확히 어떤 분모
    구조로 들어가는지
6.  시나리오별 구체적인 command 값과 범위
7.  비공개 evaluator 내부의 기타 예외 처리

따라서 위 항목을 임의로 가정하여 evaluator를 완전히 복제했다고
판단해서는 안 된다.

------------------------------------------------------------------------

## 15. 후속 질문의 의미

현재 이어서 제기된 추가 질문은 위 미확정 사항 중 특히 세 가지를
확인하려는 것으로 볼 수 있다.

### A. 세 성분 normalization 여부

`같은 비중`이 단순히 weight가 같다는 뜻인지, normalization 이후 동일
weight라는 뜻인지 확인한다.

### B. Tracking score 변환 위치

episode 평균 error를 각각 score로 변환한 뒤 평균하는지, episode 평균
error들을 먼저 합친 뒤 최종 score를 계산하는지 확인한다.

이 부분은 score 변환 함수가 비선형일 경우 실제 정책 순위와 결과 해석에
영향을 줄 수 있다.

### C. Survival episode 집계

한 로봇이 평가 도중 반복적으로 넘어져 여러 짧은 episode를 만들 경우 각
episode가 개별 Survival sample로 반영되는지 확인한다.

이 세 질문에 운영진 답변이 추가되면 evaluator 구조를 현재보다 훨씬 더
명확하게 재구성할 수 있다.

------------------------------------------------------------------------

## 16. 최종 정리

이번 공개 답변으로 자동평가는 단순한 `오래 버티기` 또는
`평균 속도 맞추기`가 아니라 다음 요소가 결합된 평가라는 점이 확인되었다.

``` text
매 step 3축 tracking error
        ↓
episode 내부 평균
        ↓
episode 단위 집계
        ↕
낙상 / reset / Survival
        ↕
10초 command resampling
        ↕
출발 및 command transition까지 포함
```

따라서 정책 개선 시에는 `Tracking`과 `Survival`을 별도 지표로 관찰하되
서로 독립적인 목표라고 가정해서는 안 된다.

현재 가장 중요한 분석 원칙은 다음과 같다.

-   장시간 생존만으로 좋은 정책이라고 판단하지 않는다.
-   평균 Tracking error만으로 좋은 정책이라고 판단하지 않는다.
-   x/y/yaw 오차를 개별 진단하면서 최종적으로는 함께 평가된다는 점을
    고려한다.
-   command 변경 직후의 transient response를 별도로 확인한다.
-   낙상 빈도뿐 아니라 낙상까지의 Tracking 상태도 확인한다.
-   동일 seed를 완전한 episode 조건 일치로 해석하지 않는다.
-   공개되지 않은 error-to-score 변환식이나 normalization을 임의로
    확정하지 않는다.

현재 답변은 evaluator를 이해하는 데 매우 유용한 구조 정보를 제공하지만,
**최종 Tracking Score의 수학적 변환과 일부 episode-level 집계는 아직
블랙박스로 남아 있다.** 후속 운영진 답변이 나오면 해당 부분을 기존 확정
사실과 분리하여 갱신하는 것이 적절하다.
