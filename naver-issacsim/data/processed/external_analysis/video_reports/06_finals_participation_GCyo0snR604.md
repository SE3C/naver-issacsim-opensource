# 1. 영상 전체 핵심 결론

영상의 메시지는 한 문장으로 압축하면 다음과 같다.

> **예선은 ‘잘 걷는 정책’을 만드는 단계이고, 본선은 그 정책을 이용해 ‘어디를 갈지, 무엇을 포기할지, 차량을 어떻게 피할지’를 전략으로 결정하는 단계다.**

본선에서는 단순히 보행 성능만 높다고 이기는 것이 아니다. 큐브를 먹으면 +100점이지만 낙상은 -50점, 차량 충돌은 -30점이므로, **어려운 큐브 하나를 먹기 위해 여러 번 넘어지는 행동은 실질적인 이득이 사라질 수 있다.** 영상은 이를 통해 “최대한 많은 큐브”보다 **기대 점수가 높은 큐브를 안전한 순서로 고르는 것**이 중요하다고 설명한다.

또한 전략 문장은 저수준 반사 제어가 아니다. 참가자가 자연어 전략을 쓰면 LLM이 다음 목표 큐브를 결정하고, 경로 계획기와 컨트롤러가 waypoint 및 속도 명령으로 바꾸며, 최종적으로 학습 정책(`PT`)이 실제 관절 토크/보행을 담당하는 계층 구조로 제시된다.

즉 본선의 핵심은 다음 세 층의 분리다.

```text
전략 텍스트
  ↓
LLM: 어떤 큐브/구역을 다음 목표로 할지 결정
  ↓
경로 계획기 → 컨트롤러: waypoint와 속도 명령(vx, wz)
  ↓
내 정책(PT): 속도 명령을 실제 보행/관절 토크로 변환
```

이 구조는 프로젝트의 `09_GAME_AGENT_NAVIGATION_SENSORS(2).md`에 정리된

```text
전략 → GameAgent → PathPlanner / Grid navigation → waypoint → 속도 명령 → 학습 정책
```

과 방향이 일치한다.

## 2.2. 02/14 — 경기 방식 (≈ 00:25–00:53)

제목:

> **1:1 토너먼트, 5전 3선승**

화면에는 H1과 Go2가 같은 경기 맵에 배치된 예시가 나타난다.

### 영상에서 직접 확인되는 경기 운영

- **BLUE와 RED가 같은 맵에 동시에 들어간다.**
- 본선은 **온라인 1:1 토너먼트** 형태로 표시된다.
- 대진은 **추첨으로 대진**이라고 표시된다.
- 본선에서 살아남은 **상위 4팀은 오프라인 결승**으로 연결된다.
- 한 대결은 **5전 3선승**이다.
- 화면에는 세트 1~5가 나타나며 먼저 3세트를 가져간 쪽이 승리하는 구조가 시각화된다.
- 하단에는 **“세트 사이 작전 시간 1분 — 전략 수정 가능”**이라고 표시된다.

### 규정 교차검증

2026 통합 규정에는 다음이 명시되어 있다.

- 예선 상위 **32팀** → 온라인 본선
- 상위 **4팀** → 오프라인 결승
- 각 대결 **5전 3선승**

따라서 영상의 경기 구조 설명은 현재 보관된 통합 규정과 일치한다.

### 전략적 의미

한 세트에서 실패한 전략을 다음 세트에서도 고집할 필요가 없다. 영상 자체가 **세트 사이 전략 수정**을 강조하므로, 본선은 단발성 프롬프트 작성보다 다음과 같은 반복 최적화에 가깝다.

```text
전략 A → 세트 결과 확인
     ↓
실패 지점 분석
     ↓
전략 문장 일부 수정
     ↓
다음 세트
```

## 2.3. 03/14 — 점수: 점수를 알면 전략이 보입니다 (≈ 00:53–01:31)

영상에서 가장 중요한 숫자 중 하나다.

| 이벤트 | 점수 | 영상 설명 |
|---|---:|---|
| 큐브 획득 | **+100** | 가까이 가면 자동 획득 (**0.7 m**) |
| 넘어짐 | **-50** | 한 번 넘어질 때마다 |
| 차량 충돌 | **-30** | 차체에 닿을 때마다 |

영상은 다음 계산을 직접 보여준다.

```text
+100 = -50 × 2
큐브 1개 = 넘어짐 2번
```

그리고 다음 메시지를 강조한다.

> **어려운 큐브 하나 먹고 두 번 넘어지면 → 본전**

> **어디를 노리고 어디를 포기할지 — 전략을 잘 짜야 합니다**

### 동점 우선순위

영상 하단에는 동점 시 비교 순서가 다음과 같이 표시된다.

1. **큐브 수**
2. **낙상 수**
3. **충돌 수**
4. **첫 큐브 시각**
5. **마지막 큐브 시각**

현재 통합 규정의 동점 기준과 동일하다.

### 중요 해석

“큐브 최대 개수”가 항상 최적 목표가 아니다.

예를 들어 어려운 큐브 1개를 얻기 위해 2번 넘어지면 순점수는 0이다.

```text
+100 - 50 - 50 = 0
```

차량 충돌까지 포함되면 오히려 손해가 될 수 있다.

따라서 전략은 단순 목표 수가 아니라 다음을 함께 고려해야 한다.

```text
예상 획득 점수
- 예상 낙상 비용
- 예상 충돌 비용
- 이동 시간 비용
- 실패 시 남은 시간 손실
```

## 2.4. 04/14 — 원리: 글 한 줄이 관절 토크가 되기까지 (≈ 01:31–02:08)

영상은 본선 제어 구조를 네 단계로 설명한다.

### 1. 내 전략

> **자연어 300자 — 어떤 큐브를 어떤 순서로**

즉 참가자가 직접 쓰는 부분은 고수준 전략이다.

### 2. LLM

> **전략을 읽고 다음에 노릴 큐브를 결정**

LLM은 관절값을 직접 만드는 것이 아니라 **다음 목표를 결정하는 역할**로 설명된다.

### 3. 경로 계획기 → 컨트롤러

```text
waypoint → 속도 명령 (vx, wz)
```

목표 큐브까지 이동할 경로를 만들고 저수준 정책이 이해할 수 있는 속도 명령으로 바꾼다.

### 4. 내 정책 (PT)

> **속도 명령 → 관절 토크 → 실제 보행**

즉 예선에서 학습한 locomotion policy가 실제 움직임을 담당한다.

화면 오른쪽에는 이 계층의 역할을 다음처럼 요약한다.

> **BRAIN — 무엇을**  
> 어떤 큐브를, 어떤 순서로, 무엇을 피할지 — 전략

### 규정/엔진 자료와의 교차검증

- 통합 규정: 전략 텍스트는 **자연어 300자 이하**
- 운영진 제공 Gemini가 **목표 큐브 우선순위**를 해석
- 프로젝트 엔진 분석: `GameAgent → PathPlanner → waypoint → 속도 명령 → 정책` 구조

영상의 아키텍처는 프로젝트 자료와 매우 잘 맞는다.

### 매우 중요한 결론

전략 텍스트로 할 수 있는 것:

- 어떤 큐브를 먼저 먹을지
- 어떤 지형을 포기할지
- 차량이 위험할 때 목표를 바꿀지
- 시간이 부족할 때 가까운 목표만 선택할지

전략 텍스트로 직접 해결하면 안 되는 것:

- 발을 몇 cm 들어라
- 관절 토크를 즉시 바꿔라
- 차량이 닿기 직전 한 프레임 단위로 회피하라

후자는 policy/controller 영역이다.

## 2.5. 05/14 — LLM의 제약: LLM은 느립니다 (≈ 02:08–02:44)

영상은 다음 수치를 명시한다.

> **한 번 답하는 데 2~3초**

따라서 LLM은 실시간 반사 신경처럼 사용할 수 없다.

### 작동하지 않는 지시 — 반사

예시:

> **“차가 오면 휙 피해라”**

화면에서 X로 표시된다.

이 지시는 차가 접근하는 순간마다 즉각적인 반응이 가능하다는 잘못된 가정을 전제로 한다.

### 작동하는 지시 — 계획

예시:

> **“차가 도는 구역은 뒤로 미룬다”**

화면에서 체크 표시된다.

### LLM에 적합한 질문

화면 하단은 다음과 같은 계획 수준의 질문을 보여준다.

- **어느 구역을 먼저 갈지**
- **어떤 큐브를 포기할지**

### 규정 교차검증

통합 규정은 실시간 반사 회피처럼 **LLM 지연을 무시한 지시**를 금지/부적절한 전략 예시로 다루고 있으며, 전략은 **구역·큐브 우선순위 수준의 계획**이어야 한다고 정리되어 있다.

즉 영상의 2~3초 지연 설명은 “LLM은 고수준 의사결정에만 사용한다”는 규정 해석을 기술적으로 설명하는 역할을 한다.

## 2.6. 06/14 — 맵에 나오는 지형과 장애물 (≈ 02:44–03:09)

영상은 본선 맵에서 사용되는 이름을 표준 용어로 정리한다.

| 이름 | 영상 설명 |
|---|---|
| **단상** | 가운데 육각 판. 위에 큐브가 놓이고 **경사로로 올라감** |
| **경사로** | 단상으로 이어지는 **18° 비탈**, 오르는 길 |
| **컨테이너** | 큰 상자. **안쪽에 큐브**가 있고 계단으로 들어감 |
| **계단** | 컨테이너 안 큐브로 오르는 길. **발을 충분히 들어야 함** |
| **박스언덕** | 박스를 쌓아 만든 지형. **맵에서 가장 어려움** |
| **박스미로** | 작은 박스가 만든 **좁은 통로**. 오르지 말고 사이로 지나감 |
| **평지** | 지상 큐브 + 미로 밖 외딴 박스 큐브. **가장 쉬움** |
| **자동차** | 정해진 경로를 계속 도는 트럭. **닿으면 -30점** |

### 매우 중요한 용어 주의

영상 하단 경고:

> **전략에 쓸 때는 이 이름 그대로 — 둔덕·험지 같은 말은 해석이 갈릴 수 있습니다**

그리고

> **포기·우선 지시일수록 표준 이름으로**

라는 취지의 강조가 나온다.

### 실전 의미

프롬프트에서 임의의 별칭을 만들기보다 다음처럼 공식 영상에 나온 이름을 그대로 쓰는 것이 안전하다.

좋음:

```text
박스언덕은 포기한다.
컨테이너를 평지보다 나중에 간다.
```

덜 안전함:

```text
험지는 건너뛴다.
높은 둔덕은 나중에 간다.
```

후자는 어떤 지형을 말하는지 LLM 해석이 흔들릴 수 있다.

## 2.7. 07/14 — 지형과 학습 포인트 ①: 지형마다 필요한 능력이 다릅니다 (≈ 03:09–03:45)

영상은 대표 지형 세 개에 필요한 locomotion 능력을 연결한다.

### 평지 — 가장 쉬움

특징:

> **장애물이 없는 땅 위에 놓인 큐브**

필요 능력:

> **속도 추종 — 시킨 속도대로 똑바로**

즉 평지는 가장 단순하지만 기본 velocity tracking 품질이 그대로 경기 효율로 이어진다.

### 박스미로 — 회전력

특징:

> **작은 박스가 만든 좁은 통로**

필요 능력:

> **회전력 — 좁은 곳에서 방향 전환**

단순 전진 속도보다 좁은 통로에서 방향을 바꾸는 능력이 중요하다.

### 단상 — 접지·추진

특징:

> **가운데 육각 판 — 경사로로 올라갑니다**

필요 능력:

> **접지력 + 추진력 — 미끄러지지 않게**

### 예선 reward와의 연결

이 슬라이드는 본선 맵을 보며 예선에서 어떤 locomotion 능력이 실제로 중요한지 역으로 이해하게 한다.

- 평지 → velocity tracking
- 미로 → yaw/turning responsiveness
- 경사 → orientation/traction/drive 안정성

다만 예선에서 참가자가 수정할 수 있는 범위는 공식 규정상 reward 파일 중심이므로, 본선 요구 능력을 보고 허용 범위를 넘어 환경/컨트롤러를 임의 변경해서는 안 된다.

## 2.8. 08/14 — 지형과 학습 포인트 ②: 컨테이너·박스언덕은 무엇이 필요한가 (≈ 03:45–04:15)

### 컨테이너 — 발 들기 높이

화면:

> **안쪽에 큐브가 있고 계단으로 올라갑니다.**

필요 능력:

> **발 들기 높이가 단 높이를 넘어야 걸리지 않습니다.**

계단 진입에서 foot clearance가 부족하면 발이 단에 걸릴 수 있다는 의미다.

### 박스언덕 — 들기 + 추진력

화면 상단 태그:

> **들기 + 추진력**

필요 능력:

> **다리 들기 높이 + 추진력 — 몸을 밀어 올릴 힘까지.**

그리고 중요한 위험이 추가된다.

> **올라섰다 떨어지면 낙상 감점 누적.**

### 전략적 의미

박스언덕은 “갈 수 있느냐”만의 문제가 아니다.

```text
성공 확률 × +100
- 실패 확률 × 낙상 횟수 × 50
- 시도에 소비되는 시간
```

까지 고려해야 한다.

따라서 정책이 박스언덕 성공률이 낮다면 **전략 텍스트에서 명시적으로 포기**하는 것이 전체 점수에 유리할 수 있다.

```text

→ KNOCKBACK 튕겨나감
```

즉 차량 충돌은 점수만 깎는 것이 아니라 자세와 경로를 망가뜨릴 수 있다.

### HIT TEST

영상 오른쪽에는 충돌 판정을 다음처럼 설명한다.

- **원형 반경** 방식: X
- **차체 표면 접촉**: O

- **H1 0.25 m**
- **Go2 0.32 m**

그리고 다음 설명이 나온다.

> **트럭이라 길쭉해서, 옆구리에 스쳐도 닿으면 충돌입니다.**

### 중요 해석

차량을 단순히 중심점과 로봇 중심점 사이 거리만으로 판단하면 실제 충돌 위험을 과소평가할 수 있다. 영상은 차량의 **실제 차체 형상과 접촉**을 강조한다.

단, 위 0.25 m / 0.32 m 수치는 이 튜토리얼 화면에서 확인된 런타임 관련 세부값이며, 통합 규정의 핵심 규칙 수치가 아니다. 최신 경기 빌드에서 변경될 가능성까지 고려해 연습 환경에서 재확인하는 것이 안전하다.

## 2.13. 13/14 — 나쁜 예 / 좋은 예: 같은 로봇, 다른 전략 (≈ 06:43–07:02)

### 나쁜 전략

영상:

> **“큐브를 최대한 많이 먹어라”**

옆 설명:

> **순서를 LLM이 마음대로 정합니다**

문장이 너무 추상적이어서 실제 경기에서 필요한 선택 기준이 빠져 있다.

문제점:

- 쉬운 큐브/어려운 큐브 우선순위가 없음
- 포기할 지형이 없음
- 차량 대응 없음
- 시간이 부족할 때 fallback 없음
- 로봇 특성 반영 없음

### 좋은 전략

영상에 표시된 예시:

> **지상 큐브부터 다 먹고 컨테이너로. 박스언덕은 포기.**  
> **차량이 5m 안이면 반대편 큐브로 바꾼다. 30초 남으면 가까운 큐브만.**

화면은 이 문장 안에서 특히 다음 요소를 구분해 강조한다.

- **우선순위**
- **포기**

실제로는 차량 대응과 시간 기반 대안까지 함께 포함되어 있어 12번 슬라이드의 “네 덩어리” 구조를 거의 그대로 구현한다.

### 왜 좋은가

이 문장은 LLM에게 자유도를 완전히 없애지는 않으면서도 **의사결정 경계**를 준다.

```text
1. 평지/지상 큐브 우선
2. 그 다음 컨테이너
3. 박스언덕은 금지
4. 차량 5m → 목표 지역 변경
5. 30초 이하 → 가까운 큐브만
```

LLM이 “무엇을 우선해야 하는지”를 매번 처음부터 추론할 필요가 없고, 정책의 약점과 경기 리스크가 전략에 반영된다.

이는 영상 제작/편집용 메모로 보이며 대회 운영 규칙으로 해석할 근거는 없다.

| practice_sim 명령 | 구체 경로/명령 표시 | 백업 엔진 구조는 지원하지만 버전별 경로 변화 가능 | **예시 명령** |

# 5. 영상이 말하는 본선의 실제 최적화 문제

영상 전체를 수학적/시스템 관점으로 정리하면, 본선은 단순한 “큐브 많이 먹기”가 아니라 다음 목적함수를 실시간으로 근사하는 문제에 가깝다.

```text
예상 최종 점수
≈ 100 × 예상 획득 큐브 수
 - 50 × 예상 낙상 수
 - 30 × 예상 차량 충돌 수
```

하지만 실제 전략에는 시간 비용도 들어간다.

```text
목표 가치
= 예상 점수 이득
× 성공 확률
- 실패 리스크
- 이동 시간
- 다음 목표를 잃는 기회비용
```

따라서 전략이 좋아지려면 큐브의 “가치”를 위치마다 다르게 평가해야 한다.

예:

- 가까운 평지 큐브: 낮은 위험, 짧은 시간 → 높은 기대가치
- 박스언덕 큐브: +100이지만 낙상 확률이 높으면 기대가치 급감
- 차량 경로 위 큐브: 충돌 및 knockback 가능성 때문에 비용 증가
- 경기 막판 먼 큐브: 도착 전 종료될 가능성 때문에 가치 감소

이 관점에서 영상의 좋은 전략 예시가 자연스럽게 이해된다.

# 6. H1과 Go2를 같은 방식으로 운용하면 안 되는 이유

영상은 같은 맵에서도 로봇마다 전략이 달라야 한다는 점을 분명히 한다.

## H1

영상 가이드상:

- 박스언덕 시도 가능
- 박스미로는 측면 접근 등 접근 방식 주의
- 계단/단상도 활용 가능

정책이 충분히 안정적이라면 수직 구조물/높은 지형의 큐브를 전략에 넣을 여지가 있다.

## Go2

영상 가이드상:

- 평지 유리
- 박스미로 유리
- 단상/컨테이너 가능
- 박스언덕은 **포기** 예시

따라서 Go2에서 “모든 큐브를 먹는다”는 전략은 정책 능력과 충돌할 가능성이 높다.

## 핵심

좋은 프롬프트는 로봇의 약점을 숨기지 않고 **약점을 전략에 명시한다.**

```text
정책이 못 하는 지형
→ 더 세게 시키는 것이 아니라
→ 목표 후보에서 제외하거나 낮은 우선순위로 둔다.
```

# 7. 차량은 왜 경로 계획 문제인가

영상은 차량을 “반사적으로 피하는 장애물”이 아니라 **전략적으로 회피해야 하는 반복 동적 위험요소**로 취급한다.

이유:

1. 차량은 정해진 경로를 계속 돈다.
2. LLM 한 번 판단에 2~3초가 걸린다.
3. 충돌은 -30점뿐 아니라 knockback을 유발한다.
4. 차량의 길쭉한 차체 표면에 닿아도 충돌이다.

그러므로 합리적인 대응은 다음과 같다.

```text
차가 지금 20cm 앞에 있다 → 즉시 회피 명령
```

이 아니라,

```text
차량 구역의 위험이 높다
→ 해당 큐브의 우선순위를 뒤로 미룸
→ 반대편 큐브로 목표 전환
→ 필요하면 그 경로의 큐브를 아예 포기
```

이다.

이것이 영상에서 “피하는 건 전략의 몫”이라고 표현한 핵심 의미다.

# 8. 영상 기반 전략문 작성 템플릿

영상의 12번 슬라이드를 그대로 구조화하면 다음 네 항목을 포함하면 된다.

```text
[우선순위]
어떤 지형/큐브부터 갈지

[포기]
정책이 불안정하거나 기대값이 낮은 지형

[차량 대응]
거리/구역/상황 기준으로 목표를 바꿀 규칙

[대안]
막혔거나 시간이 얼마 남지 않았을 때 행동
```

예시 구조:

```text
평지 큐브를 먼저 수집하고 컨테이너로 간다.
박스언덕은 포기한다.
차량이 가까우면 반대편 큐브로 목표를 바꾼다.
30초 남으면 가까운 큐브만 노린다.
```

실제 제출용 전략은 **300자 이하**, 공식 지형명을 사용하고, 현재 정책의 실제 성공률에 맞춰 작성해야 한다.

# 9. practice_sim을 영상 취지대로 쓰는 방법

영상이 권장하는 핵심은 연습 시뮬레이터를 한 번 돌리는 것이 아니라 **전략 비교 실험기**로 쓰는 것이다.

## 최소 반복 단위

1. 같은 `policy.pt` 사용
2. 전략문에서 **한 가지 규칙만 수정**
3. 같은 조건에서 실행
4. 어디서 넘어지는지, 어느 큐브를 놓치는지, 차량과 어디서 충돌하는지 관찰
5. 결과 기록
6. 다음 전략 한 줄 수정

예:

```text
A: 차량 3m 이내 정지
B: 차량 5m 이내 반대편 목표로 변경
C: 차량 경로 위 큐브 전부 포기
```

세 전략을 같은 정책에 반복 적용해 실제 점수/낙상/시간을 비교하면 “안전하지만 느린 전략”과 “공격적이지만 위험한 전략”의 차이가 정량화된다.

## 프로젝트 자료와의 연결

프로젝트의 `10_SOLUTION_AND_VALIDATION_BLUEPRINTS(4).md`는 본선 전략을

```text
고정 전략 → 규칙 기반 전략 → 필요 시 제한된 LLM
```

순으로 확장하라고 권장한다.

이 영상의 `strategy.txt → practice_sim → 결과 확인 → 한 문장 수정` 루프와 매우 잘 맞는다.

# 10. 규정상 특히 혼동하면 안 되는 부분

## 10.1. 전략과 정책은 다르다

- 전략: 어떤 목표를 선택할지
- 정책: 어떻게 실제로 안정적으로 걸을지

전략으로 locomotion policy의 물리적 약점을 근본적으로 고칠 수는 없다.

## 10.2. 외부 LLM을 경기 엔진에 임의로 붙이는 구조로 해석하면 안 된다

현재 통합 규정 기준으로는 본선의 자연어 전략을 **운영진 제공 Gemini**가 해석한다. 참가자가 별도 LLM을 경기 런타임에 반입/연동하는 구조로 이해하면 안 된다.

## 10.3. 영상의 실행 경로는 규정이 아니다

```bash
/workspace/IsaacLab/isaaclab.sh -p practice_sim.py
```

같은 경로는 실습 환경 예시다. 버전/배포 구조가 바뀌면 달라질 수 있다.

## 10.4. 연습 엔진 백업의 상수를 공식 규칙보다 우선하면 안 된다

프로젝트의 `08_GAME_ENGINE_CORE(2).md`도 연습 백업 코드의 상수·점수·타이브레이커를 공식 규정처럼 인용하지 말라고 명시한다. 점수 및 본선 규칙은 `12_2026_UNIFIED_REGULATIONS(1).md`가 우선이다.

# 11. 이 영상에서 특히 새롭게 얻을 수 있는 실전 정보

기존 규정만 읽을 때보다 이 영상에서 더 직접적으로 드러나는 실전 정보는 다음과 같다.

1. **LLM 응답이 약 2~3초**라서 반사 회피는 현실적인 사용법이 아니다.
2. 공식 지형명을 그대로 써야 LLM의 해석 모호성을 줄일 수 있다.
3. 평지/미로/단상/컨테이너/박스언덕은 서로 필요한 locomotion 능력이 다르다.
4. 영상 예시에서 H1과 Go2의 지형별 상대적인 유불리가 다르다.
5. 차량은 자동 회피되지 않으며, 전략에서 위험 구역/목표를 관리해야 한다.
6. 차량 HIT는 단순 원형 거리 판정처럼 생각하면 안 되고 **차체 접촉**을 신경써야 한다.
7. 같은 `policy.pt`라도 전략문만 바꿔 결과가 크게 달라질 수 있다.
8. 전략은 “최대한 많이 먹어라” 같은 목적문보다 **우선순위·포기·차량 대응·대안**으로 구조화하는 것이 좋다.
9. 본선 전에 `practice_sim`을 반복해 전략의 한 문장씩 수정하는 방식이 공식 튜토리얼의 권장 흐름이다.

# 12. 우리 프로젝트 관점에서의 직접적인 시사점

> 이 절은 영상/규정에서 직접 인용한 규칙이 아니라, 현재 프로젝트 자료를 함께 본 **분석적 권장안**이다.

## 12.1. 예선 정책 평가도 본선 맵 관점으로 봐야 한다

예선에서 평균 reward만 높다고 끝이 아니다.

본선 영상이 직접 요구하는 능력은 다음처럼 분리된다.

- 평지: 속도 추종
- 미로: 회전/좁은 통로
- 경사: 접지 + 추진
- 계단/컨테이너: foot clearance
- 박스언덕: leg lift + 추진 + 낙상 억제

따라서 play/evaluator에서도 이 시나리오를 가능한 한 분리해서 관찰하면 본선 전략 작성이 훨씬 쉬워진다.

## 12.2. 정책의 실패 지형을 숨기지 말고 전략의 `포기 목록`으로 바꿔야 한다

정책이 특정 지형에서 계속 실패한다면 본선 직전까지 무리하게 모든 것을 해결하려 하기보다, 그 지형을 포기했을 때 전체 기대 점수가 더 높을 수 있다.

## 12.3. 전략은 작은 규칙들의 조합으로 관리하는 것이 좋다

예:

```text
priority_v1
skip_v1
vehicle_v2
fallback_v1
```

처럼 전략을 구성요소별로 버전 관리하면 어떤 문장 변경이 점수 변화의 원인이었는지 추적하기 쉽다.

## 12.4. 본선 전략 평가 지표도 단순 최종 점수 하나만 보지 않는 편이 좋다

함께 기록할 값:

- 최종 점수
- 획득 큐브 수
- 낙상 수
- 차량 충돌 수
- 첫 큐브까지 시간
- 마지막 큐브 획득 시간
- 포기한 지형/큐브
- 목표 전환 횟수
- 정체/막힘 시간

이는 공식 동점 기준과도 연결된다.

# 14. 최종 압축 요약

이 영상은 본선을 다음과 같이 정의한다.

```text
예선
= 잘 걷는 정책 만들기

본선
= 잘 걷는 정책
+ 목표 선택
+ 지형별 우선순위
+ 포기 기준
+ 차량 위험 관리
+ 시간 기반 fallback
```

점수 구조상 다음이 중요하다.

```text
큐브 +100
낙상 -50
차량 -30
```

즉 어려운 큐브 하나를 위해 두 번 넘어지면 이득이 사라진다. 따라서 본선은 “갈 수 있는 모든 곳을 가는 문제”가 아니라 **현재 정책으로 가장 높은 기대 점수를 만드는 목표 집합과 순서를 고르는 문제**다.

전략 텍스트는 관절 제어기가 아니다. 자연어 300자 안에서 LLM이 판단할 수 있도록 다음 네 덩어리를 명확히 쓰는 것이 영상의 핵심 권장사항이다.

```text
1. 우선순위
2. 포기
3. 차량 대응
4. 대안
```

그리고 본선 전에는

```text
strategy.txt
→ practice_sim
→ 결과 관찰
→ 한 문장 수정
→ 반복
```

을 계속 수행하는 것이 공식 튜토리얼의 최종 메시지다.

- 화면에 직접 표시된 텍스트/수치 복원: **높음**
- 통합 규정과의 교차검증: **높음**
- 연습 엔진의 최신 공식 경기 빌드와 완전 동일성: **확정 불가**
- 발표자 음성의 문장 단위 완전 전사: **본 분석 범위 밖**

따라서 이 문서는 **본선 튜토리얼의 화면 기반 상세 분석 + 현재 프로젝트 소스 교차검증본**으로 사용하는 것이 가장 정확하다.
