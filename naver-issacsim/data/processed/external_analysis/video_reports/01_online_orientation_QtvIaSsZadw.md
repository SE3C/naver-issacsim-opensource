# 0. 가장 중요한 결론부터

이 설명회 전체를 관통하는 핵심은 단순히 “100시간 동안 학습을 많이 돌려라”가 아니다.

```text
질문을 만든다
↓
가설을 세운다
↓
Reward 한 가지를 바꾼다
↓
공식 서버에서 학습한다
↓
로그를 본다
↓
play로 실제 행동을 확인한다
↓
결과를 기록한다
↓
다음 가설을 정한다
```

운영진은 이 100시간을 사실상 **팀 전체가 함께 쓰는 연구 예산**으로 설명한다.

예선에서 학생이 하는 핵심 작업은:

```text
H1 / Go2
+
Reward 설계
+
강화학습
+
실제 보행 검증
+
기록
+
반복 제출
```

이다.

현재 규정까지 포함해 가장 안전하게 압축하면 다음과 같다.

```text
공식 서버
  Reward 파일만 수정
        ↓
  제출용 정책 학습
        ↓
  model_best.pt 확인
        ↓
  play 실행
        ↓
  policy.pt 생성 및 실제 행동 검증
        ↓
  env.yaml / 기술 개선 리포트와 일치 확인
        ↓
  파일 다운로드
        ↓
공식 홈페이지 제출
```

개인 PC·개인 NVIDIA 서버는 코드 읽기, 기록, 정책 재생·관찰, 비교·검증, 평가 harness 개발 등에 활용할 수 있지만 **개인/외부 GPU에서 새로 학습한 정책을 공식 제출물로 사용하면 안 된다.**

[OT]

```text
높은 mean reward ≠ 실제 예선 최고 성능
```

이기 때문에 반드시 play로 행동을 확인해야 한다.

# 24. `play.py` — 가장 중요한 검증 단계

[OT]

학습 후 반드시 `play`를 실행해 실제로 로봇이 어떻게 움직이는지 보라고 강조한다.

`play`의 역할로 영상에서 설명되는 것:

1. 로봇의 실제 보행 영상을 생성
2. 제출용 **`policy.pt`** 생성

확인해야 할 행동:

- 정상적으로 앞으로 움직이는가
- 제자리에 멈춰버리지는 않는가
- 계속 한쪽으로 휘지는 않는가
- 지나치게 흔들리지 않는가
- 기괴한 reward hacking 행동이 없는가
- 지형/명령에 맞는 행동을 하는가

학습 reward 숫자가 좋아도 실제 동작이 나쁘면 Reward를 다시 조정하고 재학습해야 한다.

# 25. 두 개의 PT 파일을 혼동하지 않기

## `model_best.pt`

- 학습 과정에서 생성/선택
- 후보 checkpoint
- 백업·검증용
- **제출 파일 아님**

## `policy.pt`

- `play`/export 흐름을 통해 생성
- 실제 행동을 확인한 뒤 제출에 사용하는 정책
- **제출 파일**

영상의 암기용 메시지를 의미상 정리하면:

```text
학습이 고른 후보 = model_best
사람이 확인하고 내보내는 제출 정책 = policy
```

## Tip 2. Reward는 한 번에 하나씩 바꾸기

가장 강하게 반복되는 연구 원칙이다.

잘못된 방식:

```text
tracking 변경
termination 변경
feet air time 변경
orientation 변경
→ 한 번에 학습
```

좋아져도 원인을 알 수 없다.

권장:

```text
baseline
↓
Reward A 하나 변경
↓
학습/검증
↓
결과 기록
↓
다음 Reward
```

## Tip 3. Reward 가중치의 균형점 찾기

- 한 Reward가 여러 행동에 영향을 줄 수 있음
- 여러 Reward가 하나의 행동을 함께 만듦
- 모든 값을 크게 키운다고 좋아지지 않음
- 속도와 안정성, 발 체공과 접촉, 에너지와 추종 등 trade-off 존재

## Tip 4. 실험 기록

매번 최소한 다음을 남긴다.

- 무엇을 바꿨나
- 왜 바꿨나
- 결과가 어땠나

이 기록은 나중에 기술 개선 리포트의 근거가 된다.

## Tip 5. 가이드북 활용

막혔을 때 서버에서 무작정 시행착오를 반복하기보다 가이드북의:

- Physical AI
- 클라우드 서버
- 학습
- 실행
- 오류 해결

내용을 확인한다.

## Tip 6. 팀원과 소통

공유할 것:

- 서버 접속 순서
- 역할
- 현재 실험
- 결과
- 다음 실험

중복 실험을 막는 것이 곧 서버시간 절약이다.

# 42. 본선과 연결되는 부분

OT는 본선 세부 규칙을 길게 설명하지 않지만 큰 구조는 분명하다.

```text
예선에서 만든 H1 / Go2 저수준 보행 정책
↓
본선에서 자연어 전략
↓
운영진 제공 LLM이 목표/우선순위 해석
↓
게임 에이전트 / 경로계획
↓
속도 명령
↓
학습된 정책
↓
로봇 행동
```

[현행 규정]

본선/결승 기준으로 현재 핵심팩에 정리된 내용:

- 온라인 본선 상위 32팀
- 1:1 토너먼트
- 각 대결 5전 3선승
- 상위 4팀 오프라인 결승
- 전략 텍스트 **300자 이하**
- 운영진 제공 Gemini가 고수준 우선순위를 해석
- 별도 LLM을 경기 런타임에 반입·연동하지 않음
- 경기시간 180초
- 큐브 +100
- 낙상 -50
- 차량 충돌 -30

OT 자체는 이 세부 숫자를 전부 설명하지 않으므로, 본선 규칙은 현재 규정집을 기준으로 사용해야 한다.

# 43. 현재 보유 경기 엔진 분석과 OT를 연결했을 때의 의미

[코드/가이드]

현재 백업의 연습 게임 엔진 분석에서는 고수준 전략과 저수준 제어가 분리되어 있다.

```text
자연어 전략
↓
GameAgent / 목표 큐브 우선순위
↓
PathPlanner / Grid navigation
↓
waypoint
↓
velocity command
↓
H1 / Go2 policy.pt
↓
관절 action
```

따라서 본선에서 LLM이 직접 관절을 실시간으로 조종하는 구조로 이해하면 잘못이다.

예선에서 만들어야 하는 것은 **명령을 안정적으로 수행하는 저수준 locomotion policy**이고, 본선 전략은 그 정책이 충분히 안정적이라는 전제 위에서 목표 선택과 위험 관리에 집중한다.

# 44. Reward 설계 관점에서 영상이 주는 실제 힌트

[OT + 코드/가이드 종합]

영상의 “하나씩 바꿔라”는 말은 단순한 교육용 조언이 아니라 매우 중요한 실험 설계 원칙이다.

Reward는 보통 다음처럼 상충한다.

```text
빠른 속도 추종
↔
자세 안정

긴 발 체공
↔
접촉 안정

큰 회전 응답
↔
진동 억제

강한 동작
↔
에너지/부드러움
```

따라서 한 번에 여러 값을 바꾸면:

- 어떤 항목이 효과를 냈는지 모름
- 성능이 나빠져도 원인을 특정하기 어려움
- 리포트에 설명할 근거가 약해짐
- 같은 실험을 다시 하게 됨

OT가 강조하는 가장 연구다운 방식은:

```text
Baseline
↓
한 변수 수정
↓
동일 조건 학습
↓
동일 play 조건 비교
↓
성공/실패 기록
```

이다.

# 45. H1과 Go2를 같은 방식으로 튜닝하면 안 되는 이유

[코드/가이드]

H1과 Go2의 취약점이 다르다.

## H1

우선 관찰할 것:

- 제자리 균형
- 전진/측면/회전 추종
- 요철/경사
- 외란 회복
- 한 발 들기/깡충거림
- 제자리 진동

## Go2

우선 관찰할 것:

- 전후/측면/회전 추종
- 험지
- ±경사
- 계단
- 착지 안정
- 미끄러짐/튀는 동작
- 발 체공 보상의 과대 여부

한 로봇에서 좋았던 Reward 가중치를 다른 로봇에 그대로 복제하면 안 된다.

# 46. 실전적으로 가장 중요한 서버 운영 원칙

OT와 현재 서버 운영 자료를 합치면 다음이 최우선이다.

## 서버에서 해야 하는 일

- Reward 변경
- 실제 학습
- 필요한 play/필수 검증
- 제출 산출물 생성

## 개인 PC에서 해야 하는 일

- 문서 읽기
- 코드 분석
- 실험 설계
- 이전 결과 비교
- 기술 개선 리포트 초안
- Git 기록
- LLM/Copilot 사용

- 공식 서버에서 생성한 `policy.pt` 실행/관찰

- 영상·로그 분석
- 평가 harness
- 본선 연습 엔진 테스트

단 **외부에서 새로 학습해 만든 정책을 공식 제출물로 사용하면 안 된다.**

# 55. 최종 결론

이 OT를 화면과 전체 음성 맥락, 현재 규정, 제공 학습·엔진 자료까지 함께 보면 대회의 예선 핵심은 **“강화학습을 오래 돌리는 것”이 아니라 제한된 계산 자원 안에서 재현 가능한 실험을 수행하는 것**이다.

가장 중요한 판단 기준은 다음 순서다.

```text
1. 규정을 지킨다.
2. Baseline을 만든다.
3. 실제 행동을 본다.
4. 가장 약한 실패 하나를 정의한다.
5. Reward 하나만 바꾼다.
6. 공식 서버에서 학습한다.
7. 로그와 play를 함께 본다.
8. 결과를 기록한다.
9. 좋아졌으면 새 기준점으로 삼는다.
10. H1과 Go2의 최고 정책을 각각 확보한다.
```

그리고 본선까지 본다면 예선에서 가장 가치 있는 정책은 단순히 training reward가 높은 정책이 아니라:

- 잘 넘어지지 않고
- 명령을 정확히 추종하며
- 여러 지형에서 재현되고
- 외란 뒤 회복하고
- 실제 `env.yaml`과 설명이 일치하며
- 반복 실행에서 안정적인

정책이다.

즉 이 영상의 진짜 메시지는 다음 문장으로 압축할 수 있다.

> **100시간을 GPU 시간이 아니라 연구 시간으로 사용하라.**
