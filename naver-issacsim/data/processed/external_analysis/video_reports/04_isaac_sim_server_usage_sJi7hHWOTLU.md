## 0. 가장 중요한 결론

이 영상이 전달하는 서버 사용 구조는 다음 한 줄로 압축된다.

```text
대회 홈페이지 팀 서버 시작
        ↓
서버가 켜진 뒤 VS Code 열기
        ↓
브라우저 code-server에서 코드 작성/수정
        ↓
Isaac Sim에서 Script Editor → File → Open
        ↓
방금 만든 Python 파일 선택
        ↓
Run으로 실행 결과 확인
        ↓
필요한 파일은 code-server에서 Download
        ↓
```

그리고 대회 전체 프로젝트 관점에서 이 흐름은 다음처럼 해석해야 한다.

```text

= 100시간이라는 제한된 팀 자원을 쓰는 곳

개인 PC / 개인 NVIDIA 서버
= 코드 읽기, 분석, 기록, 정책 관찰·검증을 최대한 담당하는 곳

```

즉, **영상은 공식 서버의 기본 조작법을 설명하고, 기존 규정/OT는 이 서버를 왜 아껴 써야 하는지 설명한다.**

```text
Team 우리 팀, 예선 1라운드가 곧 시작됩니다.
```

그 아래에는 대회 참가에 필요한 링크들이 배치되어 있다.

```text
본선 규정
```

즉 운영보드는 단순 서버 제어 페이지가 아니라 **가이드북·Discord·규정·서버를 한곳에 모은 참가자 허브** 역할을 한다.

기존 OT 분석에서도 로그인 후 팀 운영보드에서 다음 항목을 확인할 수 있다고 정리되어 있다.

- 공지사항
- 대회 관련 링크
- Isaac Sim 가이드북
- 공식 Discord
- 대회 규칙
- Isaac Sim 서버
- 파일 관련 기능
- 예선 제출
- 예선 랭킹

따라서 이번 짧은 영상은 OT에서 설명했던 운영보드 가운데 **Isaac Sim 서버 사용 부분만 다시 실습형으로 잘라 설명한 자료**로 볼 수 있다.

# 4. Isaac Sim 팀 서버 카드

영상 화면의 서버 카드에는 다음 정보가 보인다.

```text
Isaac Sim 팀 서버

1. 서버는 동시 접속이 불가합니다.
2. 서버를 사용하지 않을 시 반드시 종료해주세요.
```

그리고 현재 사용시간이 게이지와 함께 표시된다.

영상 데모 화면의 예시는:

```text
우리 팀 서버 사용 시간
4시간 57분 / 100시간
```

이다.

## 중요

여기서 `4시간 57분`은 **영상 제작용 예시 화면**이지 우리 팀의 현재 실제 사용시간이라고 해석하면 안 된다.

반면 `100시간`은 공식 규정 및 OT 자료와 일치하는 핵심 규칙이다.

### 교차검증

현재 통합 규정 기준:

- 예선 서버 시간은 **팀 합산 총 100시간**
- 라운드마다 100시간이 새로 생기는 것이 아님
- 서버를 켜고 수행하는 작업은 모두 시간에 포함
- 한 시점에는 한 명만 접속
- 사용하지 않을 때 종료

따라서 영상의 UI와 현재 규정은 이 부분에서 일치한다.

이다.

영상의 강조 문구:

```text
순서가 있습니다 — 서버 먼저, 그다음 VS Code
```

서버가 켜지면 상태 표시가 바뀐다.

대략 다음과 같은 변화가 보인다.

```text

    ↓

```

그리고 `서버 시작하기` 버튼 대신 종료 버튼이 나타난다.

영상의 데모 서버 주소는:

```text
40.robotics.connect.or.kr
```

형태로 보인다.

종료 버튼에는 예시로:

```text
서버 종료하기 (40.robotics.connect.or.kr)
```

와 같은 문구가 표시된다.

## 주의

이 주소는 영상 데모의 특정 서버 주소이므로, 실제 참가 팀은 **자기 팀 운영보드에 현재 표시되는 주소를 기준**으로 해야 한다.

영상의 의도는 특정 숫자 `40`을 외우라는 것이 아니라:

> 서버를 켜면 **우리 팀 서버 주소가 UI에 표시된다**

는 점이다.

# 7. VS Code 열기: 로컬 VS Code가 아니라 서버의 code-server

서버가 켜진 뒤 `VS Code 열기` 버튼을 누른다.

화면에서 실제 편집기 UI는 VS Code와 매우 비슷하지만 메뉴에는:

```text
Sign out of code-server
```

가 보인다.

따라서 이것은 사용자 PC에 설치된 데스크톱 VS Code를 직접 원격 연결하는 흐름이라기보다, **웹브라우저에서 제공되는 `code-server` 기반 개발환경**으로 보는 것이 정확하다.

영상에서 강조되는 내용:

```text
내 컴퓨터에 설치할 것 없음
```

즉 공식 대회 서버 사용 자체를 위해 참가자 PC에 Isaac Sim, Isaac Lab, 별도 VS Code 환경을 새로 설치할 필요는 없다는 의미다.

### 이 문구를 잘못 해석하면 안 되는 이유

우리 프로젝트에서는 개인 PC에 Isaac Sim/Isaac Lab을 구축해 검증 환경으로 쓰고 있다.

영상의 “내 컴퓨터에 설치할 것 없음”은:

```text
공식 팀 서버에 접속하고 기본 가이드 실습을 하는 데
로컬 설치가 필수는 아니다
```

라는 의미이지:

```text
개인 PC에서 별도의 분석/검증 환경을 만들면 안 된다
```

는 뜻은 아니다.

단, **공식 제출 정책을 만드는 강화학습은 운영진 제공 서버에서 해야 한다**는 규정은 별도로 유지된다.

# 8. VS Code 열기 관련 영상의 주의사항

영상에서 순차적으로 강조되는 체크포인트를 합치면 다음과 같다.

```text
✓ 켜지기 전에는 회색인 것이 정상입니다

✓ 버튼에 우리 팀 서버 주소가 나옵니다
  → 창을 닫았으면 그 주소로 다시 들어가세요

✓ 내 컴퓨터에 설치할 것 없음

✓ 팀원 동시 접속 불가

✓ 안 쓸 때는 종료
```

이 부분은 서버 운영의 핵심이다.

특히 “동시 접속 불가”와 “안 쓸 때는 종료”는 단순 편의가 아니라 100시간 자원 관리와 직결된다.

# 9. 서버 시간 100시간의 의미

이번 영상은 짧기 때문에 100시간의 운영 철학까지 길게 설명하지 않지만, 기존 OT 오디오·영상 분석에서 다음이 명확히 확인된다.

```text
100시간 = 예선 기간 전체 동안 팀이 공유하는 총 서버 시간
```

즉:

```text
학생 A 100h
학생 B 100h
학생 C 100h
```

가 아니라:

```text
팀 전체 = 100h
```

이다.

또한 라운드별 초기화가 아니다.

따라서 영상의 “안 쓸 때는 종료”는 매우 중요한 운영 규칙이다.

### 현재 프로젝트의 실전 해석

공식 서버에서 다음 작업을 오래 하면 모두 제한시간을 소비한다.

- 가이드북 읽기
- 코드 탐색
- 단순 문서 확인
- 시행착오성 편집
- 학습
- play/검증

그래서 가능하면:

```text
개인 PC
- 문서 읽기
- reward 변경안 준비
- 코드 diff 준비
- 실험 기록
- 결과 분석

공식 서버
- 필요한 수정 반영
- 실제 학습
- 필수 play
- 산출물 생성/다운로드
```

로 역할을 분리하는 것이 합리적이다.

# 11. 가이드북이 하는 역할

영상의 메시지는 “UI를 외우라”가 아니라:

> Isaac Sim을 처음 쓰는 참가자가 그대로 따라 할 수 있도록 **각 과정을 사진과 단계별 설명으로 제공한다**

는 것이다.

영상 중 다음 문구가 나온다.

```text
가이드북이 이런 식으로 전부 설명합니다
```

그리고 코드 실행 절차를 6단계로 제시한다.

기존 프로젝트의 가이드북 요약 자료를 합치면 전체 교육 흐름은 대략:

```text
시뮬레이션 / USD / 물리 기초
        ↓
로봇 불러오기
        ↓
센서 / 관측 / 제어
        ↓
강화학습 / reward
        ↓
학습 / 진단 / policy export
```

로 이어진다.

# 12. 코드 실행 표준 절차 — 6단계

영상에서 가장 실용적인 부분이다.

가이드북에 표시된 제목:

```text
코드를 넣고 실행하기 — 6단계
```

6단계는 정확히 다음 흐름이다.

```text
1. 새 파일 만들기
2. 코드 작성
3. 저장
4. Isaac Sim에서 파일 열기
5. 파일 선택
6. 실행
```

영상 후반은 이 6단계를 실제 UI로 그대로 시연한다.

# 13. 작업공간 구조

code-server의 Explorer에서 화면으로 확인되는 최상위 workspace 구조는 다음과 같다.

```text
WORKSPACE/
├── .vscode/
├── examples/
├── IsaacLab/
├── practice_sim/
├── student_workspace/
└── training/
```

이 구조는 우리가 확보한 서버 백업 구조와도 일치한다.

각 폴더의 실무적 역할은 다음과 같이 해석할 수 있다.

| 폴더 | 역할 |
|---|---|
| `.vscode` | 편집기 환경 설정 |
| `examples` | 가이드북/강의 예제 코드 |
| `IsaacLab` | Isaac Lab 프레임워크 |
| `practice_sim` | 본선 연습 시뮬레이션 관련 코드 |
| `student_workspace` | 참가자가 개인 실습 파일을 만들기 좋은 작업공간 |
| `training` | H1/Go2 강화학습 관련 코드와 가이드 |

영상에서는 주로 `student_workspace`와 `examples`를 사용한다.

# 14. 1단계 — `student_workspace`에서 새 파일 만들기

영상은 참가자가 작성하는 임시 실습 파일을:

```text
student_workspace/
```

안에 만든다.

화면 예시 파일명:

```text
test1.py
```

Explorer 상의 형태:

```text
student_workspace/
└── test1.py
```

즉 가이드북 실습용 코드를 원본 프레임워크나 학습 코드 폴더에 마구 넣는 것이 아니라, **별도 학생 작업 폴더에서 작성**하는 흐름을 보여준다.

이 습관은 매우 중요하다.

---

# 15. 2단계 — 코드 작성

영상의 `test1.py`에는 Isaac Sim에서 간단한 물리 장면을 만드는 코드가 들어간다.

화면에서 식별 가능한 주요 요소는:

```python
from isaacsim.core.api import World
from isaacsim.core.api.objects import DynamicSphere
```

계열 import와,

- 기존 `World` 인스턴스 정리
- 새 stage 생성
- `stage_units_in_meters=1.0`
- 기본 ground plane 추가
- `DynamicSphere` 생성

등이다.

또 화면에서 다음 문자열이 식별된다.

```text
/World/MyBall
```

그리고 구의 위치/색상을 NumPy 배열로 주는 코드가 보인다.

## 주의

영상 프레임에서 코드 전체가 완전히 선명하게 노출되지는 않으므로, 이 문서에서는 보이지 않는 줄을 임의로 복원하지 않는다.

핵심은 특정 코드 한 줄을 외우는 것이 아니라:

```text
code-server에서 Python 파일 작성
→ Isaac Sim이 같은 파일을 직접 연다
```

는 작업 방식이다.

---

# 16. 3단계 — 저장

영상에서는 코드 작성 후 파일을 저장한다.

VS Code의 File 메뉴에서 `Save` 계열 메뉴가 보이며, Auto Save 체크도 화면에 보인다.

다만 실전에서는 Auto Save 상태를 믿기보다 **Isaac Sim에서 열기 전에 파일이 저장됐는지 확인**하는 편이 안전하다.

왜냐하면 Isaac Sim의 Script Editor는 현재 에디터 버퍼가 아니라 **서버 파일시스템에 저장된 파일**을 읽기 때문이다.

---

# 17. 핵심 구조: code-server와 Isaac Sim은 같은 서버 파일을 본다

영상 제목 수준으로 강조되는 문구:

```text
코드 서버에서 만들고 → Isaac Sim에서 불러오기
```

이 한 문장이 서버 구조를 가장 잘 설명한다.

즉:

```text
브라우저 code-server
        │
        │ 저장
        ▼
/workspace/student_workspace/test1.py
        │
        │ 같은 서버 파일시스템
        ▼
Isaac Sim Script Editor
```

이다.

로컬 PC에서 파일을 만들고 별도 업로드하는 방식이 아니라, **서버 안의 동일 파일을 code-server와 Isaac Sim 양쪽이 공유**한다.

영상의 단계 표시:

# 20. 6단계 — Run → 결과

# 29. 영상에서 확인된 것과 기존 OT의 관계

이번 영상의 내용은 이전 온라인 설명회 OT의 서버 관련 설명과 거의 그대로 연결된다.

| 이번 영상 | 기존 OT 분석 | 판단 |

# 30. 현재 통합 규정과의 교차검증

현재 프로젝트의 단일 규정 기준은 `12_2026_UNIFIED_REGULATIONS(1).md`이다.

영상과 연결되는 규정 핵심은 다음과 같다.

## 30.1 제출 정책 학습은 공식 서버에서

```text
제출 정책을 만드는 강화학습
→ 운영진 제공 서버에서 수행
```

따라서 개인 서버에서 새 policy를 학습해 공식 제출물로 사용하는 흐름은 안 된다.

## 30.2 팀 서버 시간은 100시간

```text
예선 기간 팀 전체 합산 = 100시간
```

영상의 `/100시간` 게이지와 일치한다.

## 30.3 서버 환경 임의 변경 금지

제공 GPU 서버에:

- MCP
- 외부 에이전트
- 임의 외부 연결
- 환경 변경 목적 설치

등을 하지 않는 것이 현재 규정의 기본선이다.

영상이 아예 “내 컴퓨터에 설치할 것 없음”이라고 설명하는 것도 참가자가 **제공된 환경 그대로 쓰도록 설계**되어 있음을 보여준다.

## 30.4 결과물은 다운로드해 보존/제출

통합 규정 기준 제출은 서버 내부에서 자동 완료되는 것이 아니라 결과물을 내려받아 홈페이지에서 제출하는 흐름이다.

따라서 영상의 우클릭 `Download...`는 이후 실제 대회 작업에서도 중요한 기본 조작이다.

# 31. 영상이 직접 말하지 않지만 현재 소스상 반드시 연결해야 하는 산출물

예선 학습 이후 중요한 산출물은 다음과 같다.

| 산출물 | 의미 |
|---|---|
| `model_best.pt` | 학습 중 좋은 후보 체크포인트. 그대로 최종 제출물이라고 보면 안 됨 |
| `policy.pt` | 제출용 정책 파일 |
| `env.yaml` | 해당 정책을 만든 환경/reward 설정 기록 |
| play 영상/진단 리포트 | 실제 행동 검증 |
| 학습 로그/TensorBoard | 수렴/불안정/난이도 추적 보조 자료 |

따라서 영상에서 배운 다운로드 조작은 최종적으로:

```text
policy.pt
+ env.yaml
+ 필요한 로그/영상/기록
```

을 안전하게 외부에 보존하는 운영으로 연결해야 한다.

# 32. 우리 팀이 실제 서버를 사용할 때 가장 좋은 흐름

이번 영상과 현재 프로젝트 전체 자료를 합치면 가장 효율적인 서버 작업 순서는 다음과 같다.

## 서버를 켜기 전에 개인 PC에서

```text
1. 오늘 실험 목적 결정
2. H1 / Go2 중 대상 결정
3. 변경할 reward 하나 결정
4. old value / new value 기록
5. 가설 작성
6. 예상 학습 시간 결정
7. 실행할 명령 미리 준비
8. 다운로드해야 할 산출물 체크
```

그 다음에만 서버를 켠다.

## 공식 서버에서

```text
1. 홈페이지 → 서버 시작하기
2. 사용시간 확인
3. VS Code 열기
4. README/현재 환경 최소 확인
5. 허용된 reward 변경 반영
6. 학습 실행
7. 학습 상태 확인
8. play/필수 검증
9. policy/env/log 저장
10. 필요한 파일 다운로드
11. 서버 종료
```

## 다시 개인 환경에서

```text
1. policy 보관
2. 로그/영상 분석
3. 이전 policy와 비교
4. 실패 유형 분류
5. 다음 reward 가설 결정
```

이 흐름이 현재 프로젝트가 세운:

```text
가설
→ 한 가지 변경
→ 학습
→ play
→ 기록
→ 다음 가설
```

루프와 정확히 연결된다.

# 35. 이 영상에서 드러나는 서버의 기술적 구조

영상만으로 전체 인프라를 알 수는 없지만 사용자 관점의 구조는 꽤 명확하다.

```text
대회 웹사이트
   │
   ├─ 서버 start/stop 제어
   ├─ 사용시간 표시
   └─ 팀 서버 주소 제공
          │
          ▼
원격 GPU 서버
   │
   ├─ code-server
   │     └─ /workspace 파일 편집
   │
   ├─ Isaac Sim GUI/stream
   │     └─ Script Editor로 같은 파일 열기
   │
   ├─ IsaacLab
   ├─ examples
   ├─ training
   └─ practice_sim
```

즉 사용자는 로컬 PC를 주로 **브라우저 터미널/화면 역할**로 사용하고, 실제 개발·시뮬레이션 파일은 서버 `/workspace`에 존재하는 구조다.

# 36. “VS Code 열기”를 잘못 이해하기 쉬운 지점

영상 버튼 이름은 `VS Code 열기`이지만 실제 화면은 `code-server`다.

따라서 다음을 구분해야 한다.

```text
영상의 VS Code 열기
= 대회 서버의 웹 기반 코드 편집기 진입

로컬 PC의 VS Code
= 별도의 개인 개발환경
```

이 둘은 같은 UI 계열일 수 있지만 동일한 프로세스가 아니다.

따라서 로컬 PC의 VS Code에서 어떤 파일을 수정했다고 해서 자동으로 대회 서버에 반영되는 것이 아니다.

대회 서버에서는 서버 쪽 `/workspace` 파일을 수정해야 한다.

# 37. 서버 주소를 북마크처럼 다룰 수 있다는 의미

영상은 다음 취지의 문구를 보여준다.

```text
버튼에 우리 팀 서버 주소가 나옵니다
→ 창을 닫았으면 그 주소로 다시 들어가세요
```

즉 VS Code/서버 화면 창을 실수로 닫았다고 해서 반드시 서버를 재시작해야 하는 것은 아니다.

이미 서버가 실행 중이라면 **현재 팀 서버 주소로 다시 접속**하는 흐름을 사용한다.

이것은 서버 시간을 아끼는 데도 중요하다.

단, 실제 서버 세션/인증 방식이 바뀔 수 있으므로 항상 현재 운영보드 상태를 먼저 확인한다.

# 38. 동시접속 금지의 실전 의미

영상과 규정 모두 한 시점에 팀원 한 명만 접속하는 구조를 전제로 한다.

따라서 팀 내에서는 다음 정보를 공유해야 한다.

```text
현재 접속자
접속 시작 시각
실험 ID
예상 종료 시각
실제 종료 여부
남은 서버시간
```

예:

```text
23:10~23:40
담당: A
실험: H1-B00-5min
목적: baseline 시간 측정
끝나면 policy/log 다운로드 후 서버 종료
```

이런 방식이면 팀원이 동시에 접속을 시도하거나 서버가 켜져 있는데 또 다른 사람이 무슨 작업인지 모르는 상황을 줄일 수 있다.

# 39. 영상의 “안 쓸 때는 종료”가 특히 중요한 이유

기존 OT에서는 서버 시간을 가장 많이 잃는 경우를 단순 학습 그 자체보다 **켜 놓고 방치하는 상황**으로 강조했다.

따라서 실전에서는 작업 종료 조건을 명확히 해야 한다.

```text
학습 끝남
→ 산출물 확인
→ 다운로드
→ 기록
→ 서버 종료
```

“조금 있다 다시 쓸 수도 있으니까”라는 이유로 서버를 계속 켜두는 것은 100시간 자원 관점에서 위험하다.

# 40. 가이드북을 서버에서 오래 읽을 필요는 없는가?

영상은 가이드북을 적극적으로 사용하라고 한다. 이것은 맞다.

다만 현재 규정은 서버가 켜져 있는 시간 자체가 팀 자원을 소비한다고 설명한다.

따라서 가능한 경우:

```text
가이드북 내용 숙지
→ 서버를 켜기 전에

실제 UI 확인 / 예제 실행
→ 서버가 필요할 때만
```

으로 분리하는 것이 효율적이다.

즉 **가이드북을 쓰지 말라는 뜻이 아니라, 읽기와 실행을 분리하라**는 의미다.

# 43. 우리 로컬 환경과의 연결

이것은 이번 영상의 공식 서버 흐름을 대체하는 것이 아니라 다음처럼 보완한다.

```text
- 공식 환경 확인
- 최종 산출물 생성

- 공식 policy 재생/비교
- 로그 분석
- 자동 평가 harness
```

현재 프로젝트에서 이미 확인된 중요한 점은 대회 백업 Isaac Lab과 로컬 최신 Isaac Sim 세대가 다를 수 있다는 것이다.

따라서 로컬에서의 성공/실패를 공식 서버와 완전히 동일하다고 가정해서는 안 된다.

# 44. 이번 영상으로 새로 명확해진 점

기존 규정/OT만 읽었을 때보다 이번 영상 덕분에 실제 UI 수준에서 명확해진 점은 다음이다.

1. 서버 start/stop이 **팀 홈페이지 카드에서 직접 이루어진다.**
2. 서버를 켜기 전 `VS Code 열기`가 회색인 것은 정상이다.
3. 서버가 켜지면 **팀 서버 주소가 버튼에 표시**된다.
4. 코드 편집기는 실제로 **브라우저 code-server**다.
5. 참가자 workspace 루트에 `examples`, `IsaacLab`, `practice_sim`, `student_workspace`, `training`이 함께 보인다.
6. 일반 실습 파일은 `student_workspace`에서 만드는 흐름이다.
7. code-server에 저장한 파일을 Isaac Sim의 **Script Editor → File → Open**으로 직접 연다.
8. 양쪽이 같은 `/workspace` 파일시스템을 공유한다.
9. `examples`는 `/workspace/examples/`에 있고 강의 예제를 바로 실행할 수 있다.
10. 서버 파일은 Explorer 우클릭 `Download...`로 로컬에 받을 수 있다.
11. 최종 안내에서 모르는 부분은 가이드북 다음으로 **운영진 문의**를 권한다.

# 45. 이번 영상만으로 확정할 수 없는 것

최대한 많은 정보를 담되, 영상이 말하지 않은 내용을 억지로 넣으면 안 된다.

# 47. 실제 예선 준비 관점의 가장 중요한 연결

```text
짧은 학습

지표 확인
  ↓
play
  ↓
실제 행동 확인
  ↓
기록
  ↓
```

# 51. 프로젝트 관점의 최종 판단

이번 영상은 기술적으로 어려운 내용을 소개하는 자료라기보다 **공식 서버에서 길을 잃지 않게 해 주는 onboarding 영상**이다.

하지만 예선 준비 관점에서는 매우 중요하다. 이유는 공식 서버 100시간 중 상당 부분을 “어디서 코드를 만들지”, “Isaac Sim에서 어떻게 열지”, “파일을 어떻게 받을지” 같은 기초 조작 시행착오로 낭비할 수 있기 때문이다.

영상이 제시한 가장 안전한 표준 경로는:

```text
홈페이지
→ 서버 Start
→ code-server
→ /workspace/student_workspace 또는 허용된 training 파일
→ 저장
→ Isaac Sim Script Editor
→ Open
→ Run
→ Download
→ Stop
```

이다.

우리 프로젝트에서는 여기에 다음 원칙을 덧붙이면 된다.

```text
공식 서버는 학습에 집중한다.
읽기·분석·실험 설계는 가능한 한 밖에서 끝낸다.
한 번에 reward 하나만 바꾼다.
학습 뒤에는 반드시 실제 행동을 확인한다.
policy/env/log를 즉시 내려받아 기록한다.
서버를 켜 둔 채 고민하지 않는다.
```

이렇게 사용하면 이번 영상이 설명한 기본 조작법을 **100시간 실전 연구 운영 체계**로 확장할 수 있다.
