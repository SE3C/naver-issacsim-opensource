> 분석 대상: `[로보틱스 컵] 예선 참여 방법 [r4Zq8wQdk1Y].mp4`

> 오디오: AAC, 44.1 kHz, 2ch

## 0. 먼저 보는 핵심 결론

이 영상은 예선을 다음 한 사이클로 설명한다.

```text
보상(reward) 수정
  ↓
공식 팀 서버에서 학습(train.py, tmux)
  ↓
로그 / TensorBoard / 자동 리포트 확인
  ↓
운영진이 자동으로 고른 model_best.pt를 play.py로 실제 재생
  ↓
play 영상으로 보행을 눈으로 검증
  ↓
play 과정에서 생성된 policy.pt + env.yaml + 기술 개선 리포트 제출
  ↓
다음 라운드에서 다시 개선
```

가장 중요한 파일 구분은 다음과 같다.

- **`model_best.pt`**: 학습 과정에서 운영진 측 로직이 체크포인트 중 자동 선택·보관하는 **검증 후보/백업 모델**. 영상은 이를 그대로 제출하지 말라고 강조한다.
- **`policy.pt`**: `play.py`를 돌려 실제 행동을 확인한 뒤 생성되는 **제출용 정책 파일**. 공식 사이트의 `.pt` 업로드 칸에 넣어야 하는 파일이다.
- **`env.yaml`**: 실제 학습 설정을 기록한 파일. 기술 개선 리포트의 설명과 일치해야 한다.
- **기술 개선 리포트**: 무엇을 어떻게 바꿨고 왜 바꿨는지 설명하는 제출 요소다.

현재 프로젝트의 통합 규정과도 이 구조는 일치한다. 특히 **외부 GPU에서 새 정책을 학습해 제출하는 것은 금지**이며, 제출 정책 학습은 운영진 제공 서버에서 해야 한다.

# 4. 00:57~01:25 — 시뮬레이션 점수 70점: 정책 하나를 7개 시나리오에서 평가

## 4.1 H1의 7개 시나리오

영상 표에 표시된 H1 시나리오는 다음과 같다.

| ID | 시나리오 | 지형 | 가중치 |
|---|---|---|---:|
| H1 | 제자리 균형 | 평지 | 0.15 |
| H2 | 전진 속도 추종 | 평지 | 0.20 |
| H3 | 좌우 속도 추종 | 평지 | 0.10 |
| H4 | 회전 복합 추종 | 평지 | 0.10 |
| H5 | 약한 요철 | 요철 | 0.15 |
| H6 | 완만한 경사 ±10° | 경사 | 0.15 |
| H7 | 밀침 회복 | 평지 + 외부 충격 | 0.15 |

가중치 합은 1.00이다.

## 4.2 Go2

영상 하단에는 다음 설명이 붙는다.

> **“Go2 사족보행도 똑같이 7개 — 거친 지형·경사 ±20°·계단 10~15cm 포함”**

따라서 Go2도 7개 격리 시나리오를 사용하지만 H1보다 **험지·더 큰 경사·계단** 요소가 포함됨을 강조한다.

## 4.3 한 시나리오의 점수

영상은 시나리오 점수를 두 값의 곱으로 설명한다.

```text
생존율 × 추종 점수 = 시나리오 점수 (0~1)
```

- **생존율**: 넘어지지 않고 완주했는가
- **추종 점수**: 시킨 속도대로 움직였는가

예시:

```text
0.95 × 0.88 = 0.84
```

영상 문구:

> **“둘 다 좋으면 점수도 그대로”**

즉 빠르게 움직이기만 해서는 안 되고, **안 넘어지면서 명령을 제대로 따라야** 시나리오 점수가 높아진다.

# 17. 현재 프로젝트 소스와의 교차검증

## 17.1 확실히 일치하는 부분

### 공식 서버에서만 제출 정책 학습

현재 통합 규정은 제출 정책을 만드는 강화학습을 **운영진 제공 서버에서만 수행**하도록 한다. 개인 PC/학교 PC/외부 GPU에서 새 정책을 학습해 제출하는 것은 금지다.

영상은 주로 공식 팀 서버 사용법을 설명하며, 이 규정 방향과 충돌하지 않는다.

### 예선 서버 100시간

영상:

- 팀에 주어진 100시간을 함께 사용
- 동시에 한 명만 접속
- 안 쓸 때 종료

현재 규정:

- 팀 합산 100시간
- 한 시점 한 명 접속
- 서버 켜짐 시간이 자원 사용에 포함

서로 일치한다.

### 수정 대상 reward 파일

영상에서 H1:

```text
training/humanoid/humanoid_rewards.py
```

현재 규정에서 Go2까지 합치면:

```text

```

예선에서는 이 reward 파일을 중심으로 수정한다.

### 제출 파일

영상과 현재 프로젝트 가이드는 모두:

```text

```

를 제출 핵심으로 본다.

# 18. 영상만 보고 오해하기 쉬운 부분

## 18.1 `model_best.pt`는 제출물이 아니다

가장 중요한 혼동 포인트다.

```text
train.py → model_best.pt        # 자동 선택된 후보/백업
play.py  → policy.pt            # 확인 후 제출할 정책
```

대회 사이트의 `.pt 모델 가중치` 칸에는 영상 기준으로 **`policy.pt`**를 넣는다.

## 18.2 로그가 좋아도 정책이 좋다고 확정할 수 없다

영상은 정상 추세로:

- terrain level 상승
- velocity error 하락
- mean reward 상승

을 제시하지만, 바로 다음 파트에서 **play 영상으로 반드시 확인**하게 만든다.

즉 로그는 필터이지 최종 판정기가 아니다.

## 18.3 영상 속 reward 수치를 그대로 복사하면 안 된다

`feet_air_time`, `track_lin_vel` 등의 값은 설명용 예시가 섞여 있다.

현재 프로젝트의 권장 연구 방식은:

1. baseline 확보
2. 한 번에 하나의 reward 가설만 변경
3. 짧은 학습으로 방향 확인
4. 같은 play 조건에서 비교
5. 후보만 길게 학습

이다.

## 18.4 Go2는 “같은 iteration 수”가 같은 시간 비용이 아니다

영상 자체가 H1 약 0.6초, Go2 약 3초/iteration 예시를 보여 주며 Go2가 약 5배 오래 걸릴 수 있다고 말한다.

따라서 100시간 예산을 단순히 H1/Go2에 iteration 개수 기준으로 반반 나누는 것은 비효율적일 수 있다.

## 18.5 마감/라운드 날짜는 영상보다 최신 공식 공지가 우선

영상은 라운드가 여러 번 있다는 구조만 보여 주고 구체적인 현재 날짜를 확정하지 않는다. 실제 마감과 수정 가능 시점은 **최신 대회 사이트 공지와 단계별 규정**을 최우선으로 확인해야 한다.

# 19. 이 영상에서 도출되는 실전 예선 운영법

아래는 영상과 현재 프로젝트 소스를 합쳐 만든 **실행 가능한 해석**이다.

## 19.1 서버를 켜기 전에 로컬에서 결정할 것

- 이번 실험 로봇: H1 / Go2

- 기존 값

- 정책 메타데이터 관리

# 21. 영상의 교육적 메시지

이 영상은 단순한 “업로드 방법” 안내가 아니라, 예선의 올바른 연구 루프를 사실상 다음처럼 가르친다.

### 1. 보상 숫자를 바꾼다

정책 자체를 직접 코딩하는 대신 어떤 행동을 선호할지 reward를 조정한다.

### 2. 장시간 학습을 안정적으로 걸어 둔다

`tmux`를 사용하고 서버 시간을 낭비하지 않는다.

### 3. 로그로 망한 실험을 빨리 걸러낸다

terrain level, velocity error, mean reward를 본다.

### 4. 자동 선택 결과를 맹신하지 않는다

`model_best.pt`는 후보일 뿐이다.

### 5. 실제 행동을 눈으로 본다

`play.py`와 `play_video.mp4`가 최종 판단의 핵심이다.

### 6. 검증한 정책만 제출 형식으로 export한다

그 결과가 `policy.pt`다.

### 7. 설정과 설명을 맞춘다

`env.yaml`과 기술 개선 리포트가 모순되면 설계 의도 점수에서 불리해질 수 있다.

### 8. 라운드마다 같은 실험 사이클을 반복한다

한 번에 완벽한 reward를 찾는 것이 아니라, 제한된 서버 시간 안에서 점진적으로 최고점을 올리는 구조다.

# 22. 현재 우리 프로젝트 관점에서 가장 중요한 적용 포인트

1. **baseline을 먼저 확보해야 한다.** 영상의 지표/리포트/플레이 흐름은 변경 전 기준 정책이 있어야 해석이 쉽다.
2. **H1과 Go2의 시간 예산을 따로 보아야 한다.** 영상부터 이미 Go2가 iteration당 훨씬 오래 걸릴 수 있다고 경고한다.
3. **짧은 실험 → play 확인 → 후보만 장시간 학습**이 100시간을 가장 보수적으로 쓰는 방법이다.
4. **최적화 목표를 `Train/mean_reward` 하나로 두면 안 된다.** 영상에서도 terrain/velocity/play를 함께 본다.
5. **정책 후보 식별자를 명확히 남겨야 한다.** 어떤 `env.yaml`과 어떤 리포트가 어떤 `policy.pt`에 대응하는지 추적 가능해야 한다.
6. **제출 직전 가장 위험한 실수는 `model_best.pt`와 `policy.pt` 혼동**이다.
7. **서버에서 문서 분석·긴 고민을 하지 않는다.** 100시간은 학습과 필수 검증에 우선 사용한다.

# 24. 분석 한계

- 영상의 **화면 정보는 전체 구간을 프레임 단위로 추출해 확인**했다.
- 원본 파일에는 정상적인 오디오 트랙(AAC stereo)이 존재한다.
- 다만 현재 실행 환경에는 한국어 음성을 독립적으로 전사할 수 있는 로컬 ASR 모델이 준비되어 있지 않아, 이 문서는 **화면에 직접 표시된 텍스트·UI·코드와 프로젝트 내 기존 공식/분석 소스**를 중심으로 구성했다.
- 따라서 화면에 전혀 표시되지 않고 내레이션으로만 추가된 짧은 부연이 있었다면 일부 누락될 가능성이 있다.
- 반대로 규정/제출처럼 중요한 부분은 현재 프로젝트의 통합 규정과 교차검증해 영상 화면만으로 생길 수 있는 오해를 보완했다.
