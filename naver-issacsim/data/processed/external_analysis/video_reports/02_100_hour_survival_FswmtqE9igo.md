# 3. 타임라인 초정밀 분석

## 3.1 00:00~00:01 — 암전에서 로봇 등장

검은 배경 위에 휴머노이드 실루엣이 서서히 등장한다.

화면에는 작은 흰 글씨로:

> `지금부터`

가 보인다.

연출 의도는 “카운트다운이 시작되기 직전”의 긴장감이다. 배경을 거의 완전히 제거해 **로봇 한 대와 제한시간**에 시선을 집중시킨다.

## 3.2 00:01.5~00:08 — “100시간”

초록색 대형 텍스트가 중앙에 나타난다.

> `100시간`

그 아래에는 다음 문구가 보인다.

> `단 하나의 미션이 시작됩니다`

기존 OT 오디오 통합 분석에서도 홍보영상의 시작 메시지는 다음과 같이 확인되어 있다.

> “지금부터 100시간, 단 하나의 미션이 시작됩니다.”

### 실제 규정과의 교차검증

이 **100시간**은 단순한 홍보 문구가 아니라 실제 예선 운영의 핵심 제약과 일치한다.

현재 통합 규정 기준:

- 예선 서버 시간은 **팀 합산 총 100시간**
- 개인별 100시간이 아님
- 라운드마다 초기화되는 시간이 아님
- 서버를 켜고 사용하는 작업은 시간에 포함되는 방향으로 안내됨

따라서 영상의 첫 8초는 실제 대회 전략의 가장 중요한 제약을 정확히 잡고 있다.

### 우리가 받아들여야 할 의미

```text
100시간 = 단순 학습 시간
```

이 아니라,

```text
100시간 = 팀 전체의 제한된 연구 예산
```

으로 보는 것이 맞다.

서버에서 문서 읽기·대규모 코드 분석·불필요한 설치·장시간 LLM 대화를 하는 것보다, 이미 준비된 실험을 실행하는 데 시간을 집중해야 한다.

# 4. 00:08~00:17 — 로봇이 버텨야 하는 세계

이 구간부터 실제 Isaac Sim/Isaac Lab 계열로 보이는 시뮬레이션 장면이 빠르게 교차한다.

## 4.1 경사

화면 중앙에:

> `경사도,`

라는 강조 문구가 나타난다.

주변에는 여러 종류의 지형이 배치되어 있고 로봇들이 서로 다른 조건에서 움직인다.

### 실제 대회와의 연결

경사 주행은 공식 평가 방향과 명확하게 연결된다.

- H1: 경사 대응/균형이 주요 검증 항목에 포함
- Go2: 경사 대응이 주요 검증 항목에 포함

따라서 “경사”는 단순 장식이 아니라 실제 정책 robustness에서 중요한 축이다.

---

## 4.2 계단

곧 문구가:

> `계단도,`

로 바뀐다.

계단/단차가 배치된 여러 환경이 보인다.

### 주의

영상이 계단을 강하게 강조하지만 **예선 평가에서 H1과 Go2가 완전히 같은 계단 시나리오를 받는다고 해석하면 안 된다.**

현재 자료 기준:

- H1은 평지 균형, 전후/측면/회전 추종, 요철, 경사, 밀침 회복이 핵심
- Go2는 전진/전방위 추종, 험지, 경사, 계단, 밀침 회복 등이 주요 축

또한 H1 학습환경에는 본선 대비 고단차/계단 요소가 존재해도, 예선 자동평가 우선순위와 완전히 같다고 단정할 수 없다.

---

## 4.3 예고 없는 충격

거친 블록 지형을 걷는 휴머노이드 위로 다음 문구가 나타난다.

> `예고 없는 충격도,`

영상에서 로봇은 지형과 외란 속에서 자세를 회복하며 이동하는 모습으로 표현된다.

### 실제 대회와의 연결

이 장면은 **push recovery / 외란 회복**을 상징하는 것으로 보는 것이 타당하다.

실제 평가 방향에서도:

- H1: 밀침/외란 뒤 회복
- Go2: 밀침/외란 뒤 회복

이 중요하다.

단순히 “안 넘어졌는가”뿐 아니라:

```text
외란 발생
→ 자세 무너짐
→ 균형 회복
→ 다시 목표 속도/방향 추종
```

까지 확인해야 한다.

---

## 4.4 모두 버텨야 합니다

약 14초 전후, 실내 환경과 장애물 주변을 움직이는 휴머노이드 장면 위에 큰 초록색 문구가 나타난다.

> `모두 버텨야 합니다`

이 문장은 영상 전체의 **생존(survival)** 테마를 직접적으로 제시한다.

### 중요한 해석

강화학습 정책의 목적은 단순 최대속도가 아니다.

이 영상이 강조하는 정책의 품질은:

- 넘어지지 않는 것
- 지형이 바뀌어도 버티는 것
- 외란에서 회복하는 것
- 계속 이동할 수 있는 것

에 가깝다.

우리 프로젝트의 검증 청사진에서 강조해 온:

```text
안정성
재현성
지형 대응
명령 추종
회복 능력
```

과 정확히 같은 방향이다.

# 5. 00:17~00:26 — Reward Design

영상의 핵심 기술 장면이다.

화면 좌측에 별도의 UI 패널이 나타난다.

## 5.1 UI 제목

```text
REWARD DESIGN
TEAM 07 · 보상 설계 콘솔
```

이라고 표시된다.

이 UI 자체가 실제 참가자 서버에서 그대로 제공되는 공식 프로그램이라고 볼 근거는 없다. **홍보영상용 시각화 콘솔**로 보는 것이 안전하다.

그러나 전달하는 개념은 정확하다.

> 참가자가 강화학습에서 원하는 행동을 만들기 위해 Reward를 설계한다.

---

## 5.2 영상에 등장하는 Reward 예시

화면에 순차적으로 나타나는 항목은 다음과 같다.

```text
+1.0  전진 속도
-0.5  넘어짐
+0.2  자세 유지
```

### 이 숫자를 실제 reward 값으로 복사하면 안 되는 이유

현재 공식/백업 자료에서 실제 H1과 Go2 reward는 훨씬 많은 항목과 서로 다른 스케일을 가진다.

예를 들어 실제 설계에서는:

- 선속도 추종
- 각속도 추종
- 자세 안정
- 수직 속도 억제
- 접촉
- 발 체공 시간
- action rate
- termination penalty
- unwanted contact
- 에너지/관절 동작 관련 비용

등의 trade-off를 고려한다.

따라서 영상의 세 항목은 **Reward의 개념을 설명하기 위한 단순화된 예시**다.

### 하지만 개념적으로 중요한 점

이 세 항목은 RL 설계의 핵심 갈등을 아주 잘 보여준다.

```text
전진 속도 ↑
vs
넘어짐 ↓
vs
자세 안정 ↑
```

속도만 강하게 보상하면 빠르지만 불안정해질 수 있고,
안정성 penalty를 너무 강하게 하면 지나치게 소극적이거나 거의 움직이지 않는 정책이 나올 수 있다.

즉 Reward 설계는 단순 가중치 키우기가 아니라 **trade-off 최적화**다.

# 6. Reward 구간의 iteration 연출

보상 설계 장면에서 화면 상단에 `ITERATION` 카운터가 빠르게 증가한다.

대표적으로 프레임에서 확인되는 값:

- 약 18초: `ITERATION 120`
- 약 19초: `ITERATION 213`
- 약 22초: `ITERATION 4,926`
- 약 24초: `ITERATION 15,948`

이 값은 영상 편집을 위한 가속 연출이며 실제 학습 iteration/time 관계를 의미한다고 볼 수 없다.

같은 시점 우측 상단 `REMAINING` 시간은 약:

- `48:30:00`
- `48:29:59`
- `48:29:58`
- `48:29:55`
- `48:29:53`

등으로 표시된다.

즉 몇 초 동안 iteration은 수백→수천→만 단위로 폭증하지만 남은 시간은 몇 초만 감소한다. 이것만으로도 이 UI가 **실제 wall-clock 로그가 아니라 학습 개념을 압축한 그래픽**임을 알 수 있다.

# 7. Episode Reward 그래프

Reward Design 패널 아래에는:

> `EPISODE REWARD`

그래프가 나타난다.

그래프는 초반의 작은 진동 이후 전체적으로 상승하는 형태다.

### 영상이 전달하는 메시지

```text
Reward 설계
→ 반복 학습
→ Episode Reward 상승
→ 정책 개선
```

이라는 전형적인 강화학습 서사다.

### 실제 준비에서의 중요한 경고

우리 프로젝트 자료에서 반복해서 확인한 대로:

> **Train/mean_reward 또는 episode reward가 높다는 이유만으로 좋은 제출 정책이라고 결정하면 안 된다.**

백업 코드의 `model_best.pt` 선택도 training reward 계열 지표에 의존할 수 있지만, 실제 대회 평가는 여러 시나리오의 행동 성능을 본다.

Reward가 높아도:

- 실제로 넘어짐
- 한쪽으로 계속 회전
- 제자리 떨림
- 명령을 무시함
- 특정 지형만 잘함
- 발을 과도하게 들거나 점프함

같은 reward hacking이 생길 수 있다.

따라서 영상의 상승 그래프는 **학습이 진행된다는 시각적 상징**으로 해석하고, 실제 판단은 반드시 play/validator와 함께 해야 한다.

# 8. 00:26~00:35 — NVIDIA Isaac Sim과 병렬 환경

그리고 아래 숫자가 빠르게 증가한다.

---

## 8.1 병렬 환경 수 증가

확인 가능한 대표 화면:

```text
1 ENVIRONMENTS · PARALLEL
...
2,597 ENVIRONMENTS · PARALLEL
...
4,086 ENVIRONMENTS · PARALLEL
...
4,096 ENVIRONMENTS · PARALLEL
```

최종적으로 영상은 **4,096 병렬 환경**을 강조한다.

### 이 장면의 의미

Isaac Lab 계열 강화학습에서 GPU를 이용해 많은 환경을 병렬 실행하는 개념을 시각적으로 표현한 것이다.

전통적인 방식:

```text
로봇 1대
→ 한 번 실패
→ reset
→ 다시 실행
```

보다,

```text
수백~수천 개 환경
→ 동시에 다양한 상태/지형/명령 경험
→ 데이터 대량 수집
→ 정책 업데이트
```

가 강화학습 시간 효율에 유리하다.

---

## 8.2 4,096이 공식 고정값인가?

**아니다.**

영상에서 4,096을 보여준다고 해서:

- 공식 서버가 항상 4,096 env를 사용한다
- 참가자가 반드시 4,096으로 설정해야 한다
- 로컬 PC에서도 4,096을 실행해야 한다

고 해석하면 안 된다.

실제 적정 `num_envs`는:

- GPU VRAM
- task 복잡도
- 센서/지형 구성
- Isaac Sim/Isaac Lab 버전
- H1/Go2 환경 크기
- 렌더링 여부

등에 따라 달라진다.

특히 현재 로컬 RTX 3060 12 GB 환경에서는 처음부터 수천 env를 시도하기보다 작은 수부터 올리는 것이 안전하다.

# 9. “수천 번의 실패를, 단 몇 시간에 압축”

약 29~34초 구간 하단에 다음 문구가 나타난다.

> `수천 번의 실패를, 단 몇 시간에 압축`

이 문장이 영상의 기술적 핵심이다.

기존 OT 오디오 분석에서도 홍보영상의 메시지는:

- 실제 로봇에서 수많은 실패를 반복하는 비용과 시간을 줄이고
- Isaac Sim에서 많은 실패를 짧은 시간에 반복한다

는 내용으로 정리되어 있다.

### 강화학습 관점에서 정확한 해석

강화학습은 실패를 없애는 것이 아니라 **실패를 대량으로 싸게 생성하는 기술**에 가깝다.

```text
낙상
미끄러짐
방향 오차
과도한 회전
지형 실패
회복 실패
```

같은 경험을 반복해서 정책 업데이트에 사용한다.

영상의 “실패 압축”이라는 표현은 매우 적절하다.

# 10. 병렬 환경 장면에서 보이는 지형 구성

영상이 말하는 것은 단 하나다.

> **시간은 계속 줄어들고, 실험의 선택이 중요하다.**

# 14. 평가 UI의 숫자는 실제 공식 평가 기준인가?

**공식 규정과 동일하다고 볼 수 없다.**

특히 다음 수치는 홍보영상 연출용 예시로 보는 것이 안전하다.

- 경사 `12°`
- 마찰계수 `μ=0.05`
- 외란 `350 N·s`
- 연속 보행 `500 m`
- `SURVIVAL SCORE 92.4/100`

### 이유

현재 통합 규정의 실제 로봇별 평가는 보다 구체적인 여러 시나리오로 구성된다.

예를 들어 H1은:

- 제자리 균형
- 전진
- 좌우
- 회전
- 요철
- 경사
- 밀침 회복

등의 축이 중요하고,

Go2는:

- 전진
- 전방위 이동
- 험지
- 경사
- 계단
- 밀침 회복

등이 핵심이다.

또한 실제 로봇별 100점은 단순 `Survival Score` 하나가 아니라 현재 규정 기준:

```text
시뮬레이션 성능 70
+ 보상 변경 의도/설정 일치 20
+ 기술 개선 리포트 10
= 100점
```

구조다.

따라서 영상의 92.4/100은 **“강한 정책이 평가를 통과했다”는 시각적 상징**이지 실제 제출 결과 화면이라고 보면 안 된다.

# 15. 다만 평가 예시가 시사하는 실제 기술 목표

수치 자체는 연출일 가능성이 높지만, 네 평가 항목이 상징하는 능력은 매우 중요하다.

## 15.1 경사 지형 12°

상징:

- pitch 변화에 대한 자세 안정성
- 경사에서의 발 접촉
- 속도 추종 유지
- 올라갈 때/내려갈 때의 gait robustness

## 15.2 빙판 주행 μ=0.05

상징:

- 낮은 마찰 조건에 대한 robustness
- slip 대응
- 과도한 추진력 억제
- contact dynamics 변화에 대한 적응

단, 공식 평가가 실제로 `μ=0.05`를 사용한다고 해석하면 안 된다.

## 15.3 외란 회복 350 N·s

상징:

- impulse/push recovery
- 몸통 자세 회복
- 발 재배치
- 회복 후 command tracking 복귀

## 15.4 연속 보행 500 m

상징:

- 장시간 안정성
- 누적 drift 억제
- 작은 오류가 반복되어도 낙상하지 않는 정책
- short episode에서만 좋은 정책이 아니라 지속 가능한 gait

# 20. 영상이 생략한 실제 예선 작업

홍보영상은 56초이므로 아래 내용은 거의 보여주지 않는다.

그러나 실제 준비에서는 반드시 필요하다.

## 20.1 Baseline

아무 reward도 바꾸지 않은 원본 정책을 먼저 학습/평가한다.

왜냐하면 기준점이 없으면:

> “바꾼 뒤 좋아졌다.”

는 말을 할 수 없기 때문이다.

---

## 20.2 한 번에 하나의 Reward 변경

영상은 여러 항목을 한 화면에 보여주지만 실제 실험에서는 한 번에 하나의 가설을 검증하는 편이 좋다.

```text
Baseline
→ termination 관련 한 항목만 변경
→ 비교
```

그 다음:

```text
Baseline 또는 새 기준 정책
→ tracking 관련 한 항목만 변경
→ 비교
```

여러 항목을 동시에 바꾸면 원인 추적이 어려워진다.

---

## 20.3 play 검증

학습 reward 상승만 보고 끝내면 안 된다.

반드시 실제 행동을 본다.

확인할 것:

- 넘어짐
- 명령 미추종
- 편향 회전
- 정지 불가
- 지나친 떨림
- 발 미끄러짐
- 한 발 체공
- 과도한 점프
- rough terrain 붕괴
- 경사 진입 실패
- 밀침 뒤 회복 실패

---

## 20.4 제출 산출물

영상에는 나오지 않지만 실제로 중요하다.

```text
policy.pt
+ env.yaml
+ 기술 개선 리포트
```

`model_best.pt`는 학습 중 체크포인트/후보 파일이지 제출용 `policy.pt`와 같은 의미라고 단정하면 안 된다.

# 21. 영상의 “100시간”을 실제 운영 전략으로 번역

# 23. H1 관점에서 영상 해석

- 두 발 균형
- 자세 안정
- 전진/측면/회전 명령 추종
- 요철 대응
- 경사 대응
- 외란 회복
- 장시간 보행 중 drift 억제

### H1의 대표 실패 패턴

프로젝트 자료 기준:

- 한 발을 오래 듦

따라서 영상의 `전진 속도 + 넘어짐 + 자세 유지`라는 단순 Reward 예시는 H1의 실제 trade-off를 매우 압축적으로 보여준다.

# 25. 영상의 4,096 환경과 로컬 개발 환경


같은 식으로 대규모 환경부터 돌리는 것은 적절하지 않다.

```text

→ reward 코드가 반영되는가

→ checkpoint가 생기는가
→ play가 되는가
```

를 확인하는 데 있다.

실제 env 수는 작은 값부터 GPU 메모리를 보면서 올리는 편이 안전하다.

# 26. 영상의 평가 장면을 자체 validator 설계로 활용하는 방법

예를 들어 정책 하나를 다음 축으로 평가할 수 있다.

```text
Survival
Tracking
Rough terrain
Slope
Stairs
Push recovery
Long-horizon stability
```

그리고 한 번의 실행이 아니라 여러 seed에서 반복한다.

예:

```text
Policy A
Scenario: slope
Seed 001~010

Policy A
Scenario: push
Seed 001~010
```

기록:

- success rate
- fall rate
- tracking error
- recovery time
- body tilt
- speed
- slip
- worst-case episode

이렇게 하면 영상의 “Survival Score”를 그대로 복제하지 않으면서, 실제 정책 간 상대 비교에 사용할 수 있다.

```text
→ 본선
```

```text

=

```

영상은 성능 평가만 극적으로 보여주지만, 실제 예선에서는 설명 가능성과 일관성도 점수에 포함된다.

# 30. 영상이 암시하는 올바른 Reward 사고법

영상의 세 Reward를 개념 모델로 바꾸면:

```text
Reward =
  + 명령을 잘 따라감
  + 안정적인 자세
  + 적절한 보행 패턴
  - 낙상
  - 과도한 흔들림
  - 불필요한 action
  - slip / unwanted contact
```

이다.

그러나 어떤 항목이든 너무 크게 하면 부작용이 생길 수 있다.

### 예 1 — tracking을 과도하게 강화

- 빠르게 목표 속도에 맞춤
- 하지만 자세가 무너질 수 있음

### 예 2 — 낙상 penalty를 지나치게 강화

- 정책이 극단적으로 보수적이 될 수 있음
- 움직임 자체를 회피할 가능성

### 예 3 — feet air time 과대

- 발을 과도하게 들거나 깡충거릴 수 있음

### 예 4 — action cost 과대

- 부드럽지만 목표 속도를 못 따라갈 수 있음

따라서 Reward는 항상 영상 관찰과 함께 조정한다.

# 40. 본선과의 연결

영상 마지막이 “본선으로” 끝나지만 본선의 실제 핵심은 저수준 보행 정책만이 아니다.

프로젝트 자료 기준 본선은:

```text
예선에서 만든 저수준 H1/Go2 정책
+
고수준 목표/우선순위 전략
+
경로계획/waypoint
```

이 결합되는 구조다.

따라서 예선에서 만든 정책이:

- 저속 이동
- 방향 전환
- stop & go
- 좁은 경로
- 경사/계단 진입
- 외란 뒤 재개

를 잘 수행할수록 본선에서도 유리하다.

# 43. 최종 분석
