# Isaac Sim 정책 심층 분석 — 6영상·평가 결과 통합 ZIP

**적용 범위:** 이 프롬프트는 심층 분석을 요청했을 때 적용한다. 사용자가 최신 메시지에서 “숫자만”, “간단 비교”, “파일 존재만 확인”처럼 범위를 명시적으로 좁혔다면 그 범위만 수행한다. 영상 전체 조사나 긴 Markdown 보고서를 자동으로 덧붙이지 않는다. 기존 full 심층 요청의 기준은 아래 내용을 따른다.

첨부 ZIP을 직접 열어 평가 원자료와 영상을 조사하고, 정책이 실제로 유용한 행동을 수행하는지 판단해라. 요약표를 옮기는 데 그치지 말고 강점·실패 양상·trade-off를 찾아 다음 의사결정에 도움이 되는 단일 Markdown 보고서를 작성해라.

핵심 질문:
1. 이 정책은 목표 행동을 성공적으로 수행하는가? 생존뿐 아니라 실제 진행·추종·회복이 되는가?
2. 비교 정책이 있다면 어떤 조건에서 무엇이 좋아지거나 나빠졌는가?
3. 좋은 방향이며 다음 확인·활용 단계로 가져갈 만한가? 현재 정책 후보로 채택할 것인지, 보류할 것인지 명확히 판단해라.

자료가 허용하는 범위에서 적극적으로 결론을 내려라. 한계 설명으로 보고서를 채우거나 무조건 승자를 고르지 말고, 중요한 근거와 판단 범위를 함께 제시해라.

## 1. 입력과 분석 범위

기본 입력은 정책당 통합 ZIP 한 개다. 정책 한 개의 독립 분석, 두 개의 비교, 세 개 이상 후보의 비교 모두 지원한다. 별도의 학습 .tar.gz, native checkpoint, TensorBoard는 필수가 아니다.

현재 Windows 통합 ZIP의 주요 구성:
- 루트 MP4 6개: 지형별 시각 검증.
- source_checkpoint.txt, environment.txt, README.txt, SHA256SUMS.txt, BUNDLE_README.txt: 입력 정책과 영상 조건·구성 설명.
- evaluation/evaluation_manifest.json: robot, policy SHA, protocol, 실행·완료 상태, 환경과 source fingerprint.
- evaluation/resolved_configs.json: 실제 평가 scenario/case 설정.
- evaluation/episodes.jsonl: episode별 정량 원자료.
- evaluation/diagnostics.json: scenario별 요약 진단 수치.
- evaluation/video_evaluation_link.json: 영상과 평가의 연결.
- evaluation/evaluation.log, evaluation/README.txt: 실행·지표 해석의 보조 자료.

실제 파일 구조를 먼저 확인하고 다른 버전에도 맞춰 분석해라. 목록은 입력 확인 기준이지 모두 같은 분량으로 해설할 목차가 아니다. 요약만 읽지 말고 원자료에서 중요한 차이를 찾아라. 추가 설명·과거 보고서·학습 설정 발췌가 있으면 출처를 구분해 활용한다.

통합 ZIP만으로는 training reward, 학습 시계열, 부모 checkpoint, fresh/resume 이력이나 실제 제출 사실이 확인되지 않을 수 있다. model_XXXX 파일명이나 평가 설정으로 이를 역추정하지 마라. 학습 자료가 없다는 이유로 행동 비교 전체를 무효화하거나 학습 archive를 반드시 요청하지도 마라.

## 2. 정책 identity와 비교 조건

각 입력에 짧고 일관된 표시명을 부여하고 checkpoint 이름/SHA, robot, 완료·smoke 여부, protocol ID, seed, num_envs, case, 평가 시간, source·환경 차이를 짧은 표로 대조해라. OFFICIAL에서 학습한 checkpoint라도 Windows PERSONAL 평가 결과는 공식 채점 결과가 아니다.

영상과 평가가 같은 checkpoint에 연결되는지 metadata로 확인해라. 원 checkpoint가 ZIP에 없으면 SHA 기록의 연결이지 checkpoint 원본까지 재검증한 것은 아니다. preset/source_run_id가 비어 있으면 미확인으로 두고 임의의 Run ID를 만들지 마라. 과거 H/G/HS/GS 이름은 legacy alias로만 유지한다.

protocol ID 외에도 resolved config, source fingerprint, case, command, noise/randomization, terrain 조건을 확인해라. 다른 robot이나 호환되지 않는 평가를 동일 척도로 합치지 마라. 동일 seed/env ID는 대응 집계의 키이지 실패·reset 이후까지 동일 궤적을 보장하는 증거는 아니다. 중요한 조건 차이는 한 번 설명하고 비교 가능한 축은 계속 분석해라.

complete=false, smoke, 누락 case, fatal error는 full 평가와 구분한다. 평가 완료와 정책 품질은 별개다. 국소적인 결함이면 영향을 받는 결론만 제한한다. 필요한 identity만 선택적으로 검증하고 전체 파일을 반복 hash하지 마라. 아래 GitHub 조회는 실제 연결된 커넥터가 있을 때만 수행하며, 저장소 접근을 분석의 필수 전제로 삼지 마라.

### GitHub에서 과거 제출·공식 평가 이력 확인

개인 PC·외부 분석 AI에서 GitHub 커넥터를 사용할 수 있으면, 첨부 정책과 관련된 과거 제출·공식 점수·운영진 설명을 읽기 전용으로 확인해 이번 행동 분석의 맥락에 반영해라. OFFICIAL 서버에서 GitHub에 접속하라는 지시가 아니며, 인증정보 요청·설치·업로드는 하지 않는다.

- 먼저 `SE3C/naver-issacsim`의 `research/EXPERIMENTS.md`, `research/submission_presets/`와 연결된 제출 Release·공식 평가 기록을 조회한다. 학습 provenance는 Originals, 개인 6영상·평가는 Eval의 연결 기록을 필요한 경우에만 확인한다. 현재 robot의 기준 제출과 직접 관련된 최근 비교 기록 위주로 찾고 모든 저장소·대용량 archive를 순회하지 마라.
- checkpoint SHA → 실제 학습 Run → 제출 snapshot/policy 연결을 확인한다. 파일명·같은 설정·같은 preset만으로 해당 checkpoint가 실제 제출됐거나 그 점수를 받았다고 판단하지 마라. 연결이 확인되지 않으면 해당 공식 점수는 그 제출의 참고 이력이지 첨부 정책의 점수가 아니다.
- 관련 제출별로 라운드·제출일·정책 연결 근거·공식 시뮬레이션 총점과 시나리오별 점수를 확인한다. 설계 의도/리포트 점수는 분리한다. Survival Rate·Tracking Score는 운영진이 공개한 값만 쓰고, 총점에서 임의 역산하지 않는다. 조회한 문서/Release 링크와 조회 기준일을 남기고 공식 원문·운영진 답변과 팀의 해석을 구분한다.
- 과거 대비 어떤 시나리오가 개선/하락했으며 이번 정책이 그 약점에 어떤 행동 신호를 보이는지 연결해라. 자체 평가가 좋아져도 공식 점수 개선을 보장하지 않는다. 수치가 엇갈리면 robot·정책·조건·지표 정의 차이를 먼저 검토하고, 작은 점수 차이를 곧바로 reward 인과효과로 설명하지 마라. 공식 점수로 내부 지표를 임의 보정하거나 다음 공식 점수를 예측하지 않는다.
- 커넥터가 없거나 접근이 막히면 확인하지 못한 범위만 짧게 밝히고 첨부 ZIP 분석을 계속한다. 검색 요약만으로 값을 확정하지 말고, 기록이 충돌하면 출처와 다른 값을 함께 제시한다. 연결되지 않은 과거 수치를 기억이나 추측으로 채우지 마라.

## 3. 평가 원자료에서 핵심 차이 찾기

diagnostics.json과 episodes.jsonl을 대조하고 지표 정의·분모·집계 단위를 확인해라. 정책들을 동일 기준으로 계산하되 누락값을 0으로 채우지 마라. 중요한 축은 다음과 같다.

- 추종: mean_tracking_error, vx_error, vy_error, yaw_error, xy_rmse, yaw_rmse. XY와 yaw의 trade-off를 분리한다.
- 진행·정체: forward_progress_m, integrated_body_forward_m, world_dx_m/world_dy_m, lateral_drift_m, stall_fraction.
- 안정·회복: survived, end_reason, base_contact_failure, duration_s, roll_pitch_rms.
- 행동 비용: action_delta_rms 등 실제 필드. foot sliding/air time/관절 deviation이 기록되지 않았다면 정량값을 만들지 마라.

현재 evaluator의 주요 정의는 아래와 같으며, 입력의 버전·설명이 다르면 실제 입력 계약을 우선해라.
- mean_tracking_error는 step별 sqrt(vx 오차² + vy 오차² + yaw 오차²)의 episode 평균이다. 서로 다른 단위가 혼합된 내부 지표이므로 이 값 전체에 m/s 같은 단일 물리 단위를 붙이지 마라.
- vx_error/vy_error/yaw_error는 절대 오차 평균이며 xy_rmse/yaw_rmse와 같지 않다.
- forward_progress_m와 integrated_body_forward_m는 body-frame 실제 전진 속도의 시간 적분이며 같은 값이다. 중복 독립 근거로 세지 마라. world_dx/world_dy는 월드 위치 변화다.
- lateral_drift_m는 이름과 달리 실제 횡변위가 아니라 횡속도 추종 절대 오차의 시간 적분이다.
- stall_fraction은 명령 XY 속도 크기 >=0.2 m/s인 step 중 실제 body XY 속도 크기 <0.1 m/s인 비율이다. 분모가 되는 유효 step이 없으면 현재 구현은 0을 기록한다. 가능하면 명령 조건을 함께 확인한다.
- survived는 end_reason이 terminated가 아닌 episode다. timeout과 evaluation_end는 생존으로 기록된다. survived=false를 모두 실제 낙상이라 부르지 말고 종료/접촉 근거를 확인해라. base_contact_failure 누락은 false가 아니다.

집계는 특히 다음을 지켜라.
- scenario, case, seed를 분리하고 상행·하행 등 다른 조건을 처음부터 평균으로 묻지 마라.
- cohort는 (scenario, case, seed, env_id)다. scenario7은 고정 시간창 동안 종료 후 reset되어 여러 episode가 생길 수 있다. raw episode 수와 최초 cohort 수를 구분하고 episode ID 중복·누락을 확인한다.
- 요약 tracking error/survival은 episode 행 기준 평균·비율이다. 짧은 episode도 같은 가중치를 가지며 reset이 잦은 cohort/case의 비중이 커진다. 요약 재현에는 같은 정의를 써라.
- 중요한 실패 비교에는 cohort별 고정 시간창 내 종료 발생 여부·횟수도 확인해라. 예를 들어 한 번이라도 terminated된 cohort의 비율은 episode 실패율과 별도 지표다. 대응 키는 cohort이며 정책 간 episode ID를 1:1 짝짓지 마라.
- 실패한 짧은 episode를 삭제해 평균을 좋게 만들지 마라. 진행 거리는 생존시간 차이도 있으므로 실패/생존을 나누어 볼 때 원래 실패 빈도·분모도 남긴다.
- 전체 평균의 가중 기준을 명시한다. episode 가중 평균과 case 동일가중 평균은 다를 수 있다. 보조 재집계는 이름을 구분하고 기존 summary와 섞지 마라. scenario 평균의 단순 합을 성능 점수로 만들지 마라.
- 평균뿐 아니라 중요한 항목의 seed별 결과, 분포·하위 꼬리, 최악 case, 실패 집중도를 조사한다. 많은 env/episode를 독립 training seed로 취급하지 마라. 근거 없는 p-value·통계적 우월성은 만들지 않는다.

회전·횡이동 명령에서 world X 이동이 작다는 이유만으로 stall이라 판단하지 마라. command, body-frame 진행과 stall을 함께 본다. timeout 생존과 지형 통과는 다르다. 오차 하나나 전체 평균으로 순위를 끝내지 말고 진행·회복·자세의 손익, 높은 survival과 stall의 동시 발생, 특정 terrain의 약점을 찾아라.

## 4. 여섯 영상을 실제로 확인하고 수치와 연결

심층 분석에서는 실제 영상의 명령 시간표·전환 시점에 따라 대표 접촉·진행·회복 구간을 확인하고, 보고서에 **실제로 확인한 구간과 미확인 구간**을 간단히 남긴다. 단일 스냅샷으로 연속 완주·접촉 품질을 주장하지 않으며, 실제 시간표 없이 고정 시각이나 전 프레임 확인 완료를 만들어내지 않는다.

모든 정책의 여섯 영상을 재생하거나 실제 프레임을 조사해라. 읽을 수 없다면 정량 분석은 계속하되 영상 행동을 본 것처럼 쓰지 마라. 몇 장만 보았다면 연속 보행·진동·회복을 관찰했다고 주장하지 마라.

terrain을 대응시키고 command 시간표, push, seed, 길이, 카메라·난이도를 읽어라. Go2 현재 고정 영상은 stairs, inverted stairs, boxes, random rough, slope up/down 20°이지만 다른 robot/버전에는 실제 입력 조건을 따른다.

영상은 한 env의 시각 검증이고 camera-off 평가는 여러 seed/env/case의 별도 실행이다. 영상의 전역 command/push 시간표와 평가의 episode 기준 시간표가 다를 수 있으므로 동일 조건의 재측정으로 표현하지 마라.

각 지형에서 접근 → 장애물 접촉 → 실제 진행/정체 → 자세 손실 → 회복/실패를 따라가며 발 걸림·끌림·sliding/hopping·몸통 흔들림·방향 이탈·push 반응을 확인한다. command가 횡이동/회전으로 바뀐 구간을 전진 실패로 오판하지 마라. 추적 카메라로 화면 중앙에 있다는 이유로 제자리 보행이라 단정하지 마라.

핵심 관찰에 MP4 파일명과 시각/프레임을 남긴다. 20초 영상에서 안 넘어졌다는 이유만으로 낮은 낙상률을 추정하거나 눈대중 거리·각도·속도를 정밀값으로 쓰지 마라.

capture artifact와 행동을 먼저 구분해라. 검은 프레임·플리커링이 있으면 인접 프레임과 여러 시간대를 확인한다. 50 fps에서 0,50,100…처럼 같은 parity만 샘플링하면 black/valid 교대 패턴을 전체 검은 화면으로 오판할 수 있다. 결함을 정책 실패로 취급하지 말고 유효 관찰 범위를 밝힌다. 재렌더·원본 교체는 하지 마라.

정량 수치와 영상이 맞는지 교차검증하되 조건이 다른 관찰을 즉시 모순이라 단정하지 않는다. 영상은 수치가 의미하는 행동을 설명하며, 짧은 영상의 한 장면이 많은 episode 결과를 대신하지 않는다.

## 5. 정책의 성공 여부와 방향 판단

목표 행동 달성, 실질적 진행/추종, 안정·회복, 최악 조건과 trade-off를 종합해 판단한다. 비교 정책이 있으면 차이가 큰 축과 작거나 일관되지 않은 축을 구분해라. 전체 추천과 특정 용도별 추천은 다를 수 있다.

먼저 판단 목적을 밝혀라: 공식 제출 후보의 경쟁력인지, 광의의 지형 통과·보행 능력인지 구분한다. 현재 H1 공식 7시나리오는 제자리 균형·전진·좌우·회전 복합·약한 요철·±10° 경사·밀침 회복이며 계단·박스는 없다. 로컬 H1 scenario7은 경사 상·하를 나눈 8 case이고 계단·박스 정량 case가 없다. 실제 입력 버전과 다른 경우 입력 계약을 우선한다. 계단 영상 중앙 완주 미입증은 보조 증거 공백으로 기록하되 그 이유 하나로 H1 공식 후보를 자동 REJECT하지 마라. 반대로 보조 지형 성공으로 공식 성능을 보증하지도 마라. 제출 목적과 보조 행동 목표의 판정이 다르면 따로 명시한다.

아래 상태는 학습 가설이나 공식 제출 상태가 아니라 이번 자료의 정책 후보 판단이다.
- PROMOTE: 중요한 목표와 경쟁 후보 대비 이점이 확인되어 다음 확인·활용 단계로 가져갈 가치가 있음.
- HOLD: 유용한 신호는 있으나 중요한 trade-off/약점/미확인 조건 때문에 채택을 보류함.
- REJECT: 해당 목표에 뚜렷한 실패·비용이 크거나 비교 후보보다 불리해 현재 후보로 권하지 않음.
- 판단 불가: 핵심 평가/identity/영상 근거가 깨져 해당 질문에 답할 수 없음. 영향을 받지 않은 관찰은 유지함.

성공적이라는 말은 목표 행동 수행, 비교 후보 대비 개선, 다음 후보로서의 가치 중 무엇인지 명확히 해라. evaluation COMPLETE를 학습·제출 성공으로 바꾸지 마라. 자료가 충분한 축에는 분명하게 판단하고 작은 차이를 자동으로 잡음이나 확정적 우월성으로 처리하지 마라.

공식 채점 함수·공통 calibration이 제공되지 않았다면 70/100점 환산이나 임의 합산점수를 만들지 마라. official_score=false/raw diagnostics는 내부 진단으로 유지한다. 행동 차이는 확인할 수 있어도 reward 변경의 인과효과·학습 중 변화는 별도 근거가 필요하다. 학습 자료가 없으면 범위를 한 번 짧게 밝힌 뒤 행동 분석에 집중한다.

핵심 발견은 관찰·해석·반대 근거를 연결한다. 가능한 행동 기전은 설명할 수 있으나 측정되지 않은 관절/reward 원인을 확정하지 마라. 한계와 경고를 여러 절에서 반복하지 않는다.

## 6. 보고서와 다음 행동

완결된 단일 Markdown 보고서 한 개를 제공해라. 권장 구성:
1. 결론: 정책별 성공 여부·후보 판단·추천과 가장 큰 trade-off.
2. 정책과 비교 조건: checkpoint identity, 평가 범위와 중요한 차이.
3. 정량 비교: 핵심 수치 표, case/seed/분포·실패 집중도와 주요 발견. GitHub에서 관련 공식 이력을 확인했으면 과거 제출 점수·주요 시나리오 변화와 이번 내부 진단의 연결/차이를 짧게 덧붙인다.
4. 6지형 행동 비교: 시각/프레임 근거, 실제 진행·회복과 수치의 일치/차이.
5. 종합 판단: 좋은 방향인지, 강점·치명적 약점, 추천 범위.
6. 다음 행동 한 가지와 필요한 추가 근거, 재확인 가능한 파일 목록.

한 정책이면 상대적 우월성을 만들지 말고 목표 행동과 약점을 평가한다. 세 개 이상이면 대칭적으로 비교하고 유리한 일부 조건만 골라 승자를 만들지 마라. 표를 지나치게 늘리지 말고 중요한 차이의 설명에 집중한다. 학습 자료가 없는데 빈 TensorBoard/학습 계보 절을 만들지 마라.

다음 행동은 기존 원자료·영상으로 해결할 수 있는 것부터 추천한다. 새 학습·평가를 기본 결론으로 삼지 말고 필요할 때만 어떤 불확실성을 해결하며 판단이 어떻게 달라지는지 적어라. 근거 없는 10% 개선 같은 합격 문턱은 만들지 마라.

다음 학습이 필요하다면 config 탐색(설정의 trade-off), 독립 학습 seed 반복(재현성), 고정 config 추가 학습(학습량·후반 안정성), reward 전환 resume(경로 효과) 중 어떤 질문인지 선택하고 비교 대상·시작점·예산·판단 시점을 적어라. 평가 seed/env 수를 독립 학습 반복으로 세지 마라. 무기한 resume, 공격적 다중 reward 변경, 촘촘한 미세 sweep을 기본 해법으로 삼지 마라. 최근 HOLD 반복만으로 모든 개선이 없었다고 단정하지 말고 내부 행동 변화·공식 점수·재현성의 근거를 분리한다. 로컬 순위는 공식 점수 예측이 아니다. 이미 끝난 비교를 다시 미실행으로 제안하지 않는다.

직접 계산한 수치와 요약 인용을 구분하고 중요 수치에 ZIP 내부 파일·scenario/case·집계 기준을 남긴다. 작성 후 정책 방향, checkpoint SHA, 단위·분모, 실패/생존, 영상 위치가 뒤바뀌지 않았는지 확인해라. 영상 미확인·capture 결함은 해당 주장 옆에서 간결하게 밝힌다.

보고서 파일명은 <ROBOT>_<정책구분명들>_POLICY_COMPARISON_<YYYYMMDD>.md로 하고 하나만 분석하면 POLICY_ANALYSIS를 사용한다. 이름에 추정 Run ID를 넣지 마라. 최종 전달은 보고서와 이번 분석에서 실제 생성한 표·CSV·코드 등 필요한 재현 파일을 묶은 단일 ZIP으로 한다. 입력 ZIP·영상 전체를 이유 없이 중복 포장하지 마라. 마지막 채팅은 핵심 결론과 결과 ZIP 링크만 짧게 남겨라.

이 요청은 제공 자료의 분석과 새 보고서 작성만 허용한다. 학습·GPU 평가·렌더링·export·서버 종료·외부 게시·원본 수정/삭제는 실행하지 마라.
